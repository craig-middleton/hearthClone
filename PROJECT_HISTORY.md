### 2. The Taunt refactor
The rule was previously duplicated across three call sites (`EffectTester.OnMinionClicked`, `EffectTester.OnFaceClicked`, `AIController.TakeTurn`), while `Combat.TryAttack` — the one chokepoint every attack passes through — had no idea Taunt existed. It was moved to live solely inside `Combat.TryAttack`.

An **intermediate version passed a `List<Minion> defenderTaunts` parameter instead**, chosen to keep `Core.Combat` decoupled from `Board`. That was abandoned during review: a `null` list would have silently disabled the Taunt rule entirely — the exact silent-failure mode the refactor existed to eliminate, just relocated. Passing `Board` + the defending `Player` and letting `TryAttack` call `GetTauntMinions` itself closed the hole, and as a bonus restored the owner-named failure message. `Board` lives in `Core` alongside `Combat`, so there was never an assembly obstacle — the original objection was a misreading of the no-singletons preference as "avoid parameters".

*(Session 28 went further and removed the `defender` parameter too — see below.)*

## Session 30 — card size parity, and the spell-cast animation vertical slice

### 1. `MinionView`/`CardView` size parity (Live Constraint 14)
Craig had manually resized `MinionView`'s root and `ArtworkImage` to 160x220 to match `CardView`, so board minions and hand cards render at the same size. After that change, minions *with* artwork (Goblin) still appeared to render larger on the board than minions without (Wisp, Warhorse, Murloc) — same prefab, same `LayoutElement`.

Investigated in the order the task specified: (a) `BoardPanel`'s `HorizontalLayoutGroup` sizes every child from the same fixed `LayoutElement` (160x220 for every instance), so it can't explain a per-card difference on its own; (b) `ArtworkImage` was point-anchored (`AnchorMin == AnchorMax == 0.5,0.5`) with a `SizeDelta` hand-matched to 160x220 — an *absolute* size, not one that tracks the parent; (c) confirmed algebraically that every `MinionView` root resolves to the identical size regardless of artwork, since `LayoutElement.minWidth`/`minHeight` are unset (0) uniformly, so a width shortfall shrinks every card by the same ratio.

The real mechanism: when the board has enough minions to exceed the panel's width, the layout group shrinks every root below 160x220 — but `ArtworkImage`, a grandchild rather than a direct child, is invisible to the layout group and stays fixed at 160x220, overflowing past the shrunk card. Invisible on cards with no artwork (`Image.enabled = false`), visible on Goblin. **The apparent size difference was an illusion** — root sizes were identical the whole time. Fixed by switching `ArtworkImage` to stretch anchors (`0,0`→`1,1`, `SizeDelta 0,0`) so it always exactly fills whatever size the root actually resolves to, compressed or not.

Couldn't verify live in Play mode — Craig's Unity Editor had the project locked, so a second batch-mode instance couldn't open it to instantiate and inspect at runtime. The fix is deterministic anchor math, not something that needed runtime confirmation, but this is worth flagging: a future session hitting the same lock should either ask Craig to close/unfocus the Editor for a batch-mode check, or accept the same static-analysis approach and say so explicitly rather than claim an unverified runtime check.

Also confirmed **`MinionView` has never had a `costText` field** — board minions have never shown mana cost, not a regression from the resize. Asked Craig explicitly rather than adding the field speculatively; answer was leave it as-is (matches real Hearthstone, which doesn't show cost on played minions either).

### 2. Spell-cast animation — planning, then the vertical slice

**Planning pass.** Read `CardEffect.Execute()`, `DealDamageEffect`, `GainManaEffect`, and how `EffectTester.OnCardClicked`/`PlayerHand.PlayCard` resolve a spell play, before proposing anything. Key finding: `PlayerHand.PlayCard` mutates mana/hand/effect all synchronously in one call, and `HandDisplay.RenderHand` (called from `AfterGameAction()` right after) destroys and rebuilds every `CardView` from the post-mutation `Hand` list — same frame. There is currently no persisting visual object to animate mid-sequence; that's the central architectural obstacle for a four-beat animation, not a missing tween library.

Recommended (Option A, accepted): keep `CardEffect.Execute()` synchronous and keep `Effects.asmdef` completely animation-ignorant — state mutates instantly as it does today, and the animation sequence is a purely visual overlay built entirely in `UI.asmdef`. The alternative (Option B — split `PlayCard` into validate/commit phases so damage lands on visual impact, matching real Hearthstone's timing exactly) was flagged as a possible phase-2, not needed to make the sequence look right for a first pass, and it would touch `Cards.asmdef`, which Option A leaves untouched entirely.

Tooling survey: no coroutines, no `ParticleSystem`, no Animator usage anywhere in the project — `FaceView`'s idle sway (`Update()` + sine math) is the only existing "animation," and is the precedent this feature follows. No DOTween/LeanTween in `Packages/manifest.json`. Recommended plain coroutines + `AnimationCurve`, consistent with that precedent, and explicitly recommended against Animator (state-machine overhead for four short procedural beats) and against Timeline (installed but wrong tool — it's for hand-authored sequences, not a system needing to resolve an arbitrary runtime source/target pair).

Build order recommended: travel + impact reaction first (needs zero architecture change — `FaceView` persists across refresh, so both source and target can be handled without touching the destroy/rebuild pattern), then lift/zoom (first piece that actually needs the destroy-timing problem solved), then discard-off last (same fix, plus a new discard-pile anchor that doesn't exist yet). Craig confirmed this plan and asked for the vertical slice built and reported back before anything past it.

**The order-of-operations question, and why it mattered.** Before building, Craig asked to confirm explicitly whether the sequencer captures the `CardView`'s position *before* `PlayCard` runs. Checking `CardView.SetCard`/`HandDisplay.RenderHand` showed the click callback only ever carried `CardData` — `Action<CardData>` — with no way to reach the clicked `CardView` at all. That had to change: `CardView.SetCard`, `HandDisplay.RenderHand`, and both `EffectTester` click handlers now thread `Action<CardData, CardView>` instead, invoked as `onClicked?.Invoke(card, this)` at the moment of the actual click, while the `CardView` is still guaranteed alive.

Inside `OnCardClicked`, the position is captured as a plain `Vector3` — `cardView.transform.position` — *before* `PlayCard()`/`AfterGameAction()` run, specifically because `RefreshHandDisplay()` (called synchronously from `AfterGameAction()` right after) destroys that exact `CardView` in the same frame, before any coroutine would get a second frame to read a live `Transform` off it. A live `Transform` reference carried into the coroutine would not have survived; the `Vector3` snapshot does, because the projectile the sequencer spawns is its own GameObject, entirely decoupled from the `CardView`'s fate. This is now Live Constraint 15.

**What got built.** `SpellAnimationSequencer.cs` — new file, spawns a plain runtime `Image` (no new prefab or particle asset needed) and lerps it from the captured source position to the (live, persistent) target `Transform` over an `AnimationCurve`, re-sampling the target's position every frame since `FaceView`'s idle sway is running concurrently. On arrival it destroys the projectile and, for damage effects, calls a new `FaceView.PlayDamageReaction()`.

`FaceView.PlayDamageReaction()` is deliberately color-flash only, not shake. `FaceView.Update()` already drives `avatarRect.localPosition`/`localScale` every frame for the idle breathe/sway; a reaction that touched position or scale from outside `Update()` would just get overwritten the next frame instead of composing with it. Color is untouched by the existing `Update()`, so it's the safe surface to animate from outside. Shake is a legitimate later addition, but needs `Update()` itself taught to combine a shake offset with the sway base — not something to bolt on from the sequencer without touching `FaceView`'s existing animation loop.

Heal/buff glow (the fourth reaction type in the original ask) isn't wired at all — there's no `CardEffect` subtype to key off yet (`GainManaEffect` is self-targeted mana gain, not a heal). Left as a comment at the call site rather than stubbed.

`EffectTester.ResolveViewTransform(Target)` was written generically against `Target.TargetPlayer`/`TargetMinion` even though the `Minion` branch is unreachable today (spells can only target a face) — per the plan, so the animation's targeting doesn't need rework once minion-targeting for spells lands; it just needs `BoardDisplay` to start tracking a `Minion → MinionView` mapping, which doesn't exist yet.

**Compile verification hit Live Constraint 13 directly.** After creating `SpellAnimationSequencer.cs`, `dotnet build UI.csproj` failed with `CS0246: SpellAnimationSequencer could not be found` — not a code error, but the Unity-generated `.csproj` not yet regenerated to include the new file, because Craig's Editor window wasn't focused and hadn't reimported it. Waited ~100s with no pickup; asked Craig to focus the Editor. Once focused, the `.meta` file appeared within moments and all five assemblies built clean, confirmed both via `dotnet build` and Unity's own `Editor.log` showing no `error CS` lines.

**Confirmed via playtest**: Craig wired the `SpellAnimationSequencer` component (the one manual step — same pattern as every other view reference on `EffectTester`, dragged into the Inspector, no code-side wiring) and played Fireball/Arcane Bolt against the opponent's face. Travel effect and impact flash both fired correctly.

## Session 31 — the targeting system

Spells had only ever been able to hit the enemy face. This session let a spell target a minion (either side) or either face, via click-a-card-then-click-a-target: `CardData.targetsSelf: bool` was replaced with `TargetRequirement { None, Self, Any }`, and `EffectTester.ResolveSpell` resolved the click-then-click flow (a card clicked once entered a "pending" state, a second click on a valid target resolved it).

**Two real bugs found and fixed.** First, a lethal spell hit on a minion could destroy the target's `Transform` mid-animation — `SpellAnimationSequencer` was reading `targetView.position` unconditionally every frame of the travel coroutine, and `EffectTester.AfterGameAction()` (`RemoveDeadMinions()` → `RefreshAll()`, both synchronous) destroyed the dead minion's view before the coroutine's next `yield` resumed, throwing `MissingReferenceException` on an exactly-lethal cast. Fixed by having `TravelAndReactRoutine` re-check `targetView != null` every frame (Unity's overloaded `Object` equality correctly flags a destroyed-but-not-nulled reference) and fall back to the last sampled position, skipping the end-of-travel reaction call the same way if the target is gone — this became Live Constraint 16, and the same fix carried forward unchanged through drag-and-drop (session 32) and the `MinionView`-hold work later. Second, a duplicate-card pending-selection identity quirk: pending selection was tracked by hand index (`pendingSpellHandIndex`), which worked but was fragile — documented at the time as the old Constraint 17, since removed entirely once drag-and-drop deleted the click flow it described.

**Playtest-confirmed, fully:** exactly-lethal minion hit (no crash, confirming the Constraint 16 fix); non-lethal minion hit (target's idle sway visibly continued through the travel animation — confirmed the null-check-and-fallback approach over an unconditional position snapshot, which would have silently killed that sway for every cast); exactly-lethal face hit (clean win, no crash — confirmed `FaceView` was never reachable by the Constraint-16 bug class, since `RefreshFaceDisplay` only calls `SetPlayer()` on the existing instance rather than destroying it); own-minion targeting (Player Two self-killed their own Shieldbearer with Arcane Bolt — no side restriction on spell targets, and dead-minion cleanup handled a spell-killed friendly correctly); duplicate-card cancel/reselect (clicking the second copy of a pending card moved the highlight rather than cancelling); self/none-target spells (Mage Pupil played instantly, no pending-state UI); manual control mode (Player Two cast a targeted spell through the same flow); console clean, no leftover debug logging.

## Session 32 — drag-and-drop replaces click-to-play

Click-to-play (and the click-then-click targeting flow from session 31) was replaced entirely by dragging a card onto a target — the only way to play a card from here forward; click-to-attack was untouched. `CardView` implements `IBeginDragHandler`/`IDragHandler`/`IEndDragHandler` directly, cloning itself into a semi-transparent, non-raycastable ghost parented under the root `Canvas` on drag start (so it survives independently of `handPanel`) and tracking the pointer via `RectTransformUtility.ScreenPointToWorldPointInRectangle`. `EffectTester.ResolveCardDrag` (later extracted to `CardDragResolver`, session 33) centralises drop resolution via `EventSystem.RaycastAll`: minion → friendly board only, `Any`-target spell → any `MinionView`/`FaceView` hit, `None`/`Self` → any recognized zone. `CanPlayerOneDrag`/`CanPlayerTwoDrag` became the single gating source for both drag initiation and drop resolution, replacing the scattered checks the click flow had.

**One real bug found and fixed**: `boardPanel`/`opponentBoardPanel` had no raycastable `Graphic` covering their bounds, so `EventSystem.RaycastAll` returned zero hits over empty board space — a drop meant for open board (a minion summon, or a `None`/`Self` spell) silently failed. It first surfaced as an apparent Player-Two-only gating bug (a `[DragDiag]` trace showed the callback firing and correctly rejecting on zone-recognition, which sent the investigation down a wiring path before the wider case — Player One's drop on empty space — was tested and found to fail identically). The real bug was universal to both players and specific to empty board space. Fixed via `BoardDisplay.Awake()` → `EnsureRaycastCatcher()`, adding a fully transparent, `raycastTarget = true` `Image` directly on `boardPanel`'s own GameObject (not a child, since `RenderBoard()` destroys all children every refresh) — this became Live Constraint 18.

## Mulligan batching fix (Next Steps 6)

The old per-card `MulliganCard()` did remove → add-to-deck → shuffle → draw *per card*, so a card mulliganed early in a multi-card mulligan could be shuffled back into the deck before later draws in the same batch resolved — a card you'd just returned could come right back. Replaced with `PlayerHand.MulliganCards(List<CardData>)`: removes **all** selected cards from `Hand` first, draws replacements from the deck as it stood with every set-aside card excluded, and only *then* adds the set-aside cards back and shuffles once — matching real Hearthstone's batching. Both `MulliganController.OnConfirmMulliganClicked` and `AIController.PerformMulligan` updated to collect their full selection and call `MulliganCards` once instead of looping.

**Playtest-confirmed**: mulliganing the entire opening hand (3 cards) produced a replacement hand with zero overlap against the set-aside cards. A second test mulliganing a single Watchman drew another Watchman — investigated and confirmed a false alarm (the deck's untouched second copy, not the returned card being handed straight back). Closed out on code reasoning rather than further probabilistic testing: `MulliganCards` removes every set-aside card from `Hand` before any `DrawCard()` call runs and only re-adds them to `Deck` afterward, so a draw inside that method returning a still-removed card is structurally impossible, independent of card-name duplicates. **Approved deliberate behaviour change**: since set-aside cards are no longer temporarily back in the deck before each draw, mulliganing more cards than remain in the deck can now trigger fatigue where the old code wouldn't — only reachable with a near-empty deck, not a realistic 30-card game start, and correct "draw before shuffle-back" behaviour rather than a regression.

## Held-minion hold/layout investigation (2026-08-31) — three bugs, two fix attempts, then the final two-channel fix

Found via the Arcane-lethal spell-burst playtest (Next Steps 18, step 3, spell VFX plan) — the same session that wired `SpellBurstFactory.CreateArcaneBurst` into `SpellAnimationSequencer`. This is the full investigative record behind Live Constraint 23 in STATUS, which now states only the final architecture.

### Bug 1 — held view snapped to the board's leftmost slot

A burst rendered far to the left of its target minion's actual on-screen position. Traced to `BoardDisplay.RenderBoard`: its destroy loop skips a held child (Constraint 22), so the held child keeps its *old* sibling index, but the rebuild loop `Instantiate`s fresh views for every surviving minion as *new* children appended after it — so a minion that died mid-row ends up at sibling index 0 once its still-held view is the only survivor of the old set. `BoardPanel`/`OpponentBoardPanel` both carry a `HorizontalLayoutGroup` (and `MinionView`'s prefab a `LayoutElement`), so sibling index drives horizontal position directly — the layout group snaps the held view to the leftmost slot regardless of where it actually died. `SpellAnimationSequencer`'s position tracking (`lastKnownTargetPosition`, Constraint 16) was never the bug — it re-samples `targetView.position` live and faithfully reports wherever the view *actually* is; the view itself was silently misplaced upstream.

**Not Arcane-specific** — same shared `BoardDisplay`/`MinionView` code path Fire's lethal case also goes through. Re-verified specifically for this fix: Fire's lethal case against a non-leftmost minion showed the identical leftward-snap bug, confirming it went unnoticed in the original Fire playtest (Next Steps 18 step 2) only because that test's target happened to already be in the leftmost slot (sibling index 0 is a no-op for this bug) and/or because Fire's large, chaotic burst visually masked a modest offset that Arcane's tight, deliberate swirl made obvious.

**Fix attempt 1**: `MinionView.BeginHold`/`EndHold` toggled `LayoutElement.ignoreLayout` (`true` on the first hold, `false` back once the hold count returns to zero, including via the TTL-expiry path) — pulling the held view out of the `HorizontalLayoutGroup`'s control entirely, freezing it exactly where it visually sat at the moment it was held, fully decoupled from whatever reflow happened to its rebuilt siblings.

**Rejected alternative, considered at the time**: restoring the held view's original sibling index (`SetSiblingIndex`) instead of excluding it via `ignoreLayout`. Rejected because a `HorizontalLayoutGroup` recalculates *every* child's position on any change to the group's children, not just the moved one, so the held view's pixel position still wasn't guaranteed stable if the surviving siblings' count/spacing changed elsewhere in the row during the hold window; layout exclusion was also considered the semantically correct behavior at the time — a dying minion should die where it stood, not snap to a recalculated layout slot mid-animation. (This reasoning was later superseded — see Bug 3 below, where staying a *counted* participant turned out to be necessary after all, just combined with a pinned rather than free-floating sibling index.)

**Applies wherever else the hold mechanism reaches a layout-group-controlled panel**: `CardView`/`HandDisplay` are the next intended callers of the identical `BeginHold`/`EndHold` pattern (Constraint 15, Next Steps 17, for lift/zoom and discard-off) — confirmed (this session, `TestScene.unity`) that `HandPanel`/`OpponentHandPanel` **both also carry a `HorizontalLayoutGroup`**, so this was not a hypothetical for future work.

### Bug 2 — held view drew behind its rebuilt siblings

Same session, after the `ignoreLayout` fix landed: position was then confirmed correct (Fire and Arcane both re-tested against a mid-row minion), but the held view started rendering *behind* its surviving siblings instead of in front of/alongside them.

**Root cause**: `ignoreLayout` only excludes the held view from the `HorizontalLayoutGroup`'s **position** math — it does nothing to sibling index, and sibling index is what independently controls **draw order** in this project's setup (`MinionView`'s prefab carried no `Canvas`/`overrideSorting` of its own at this point, so it drew purely by sibling position within `GameCanvas`, a single `Screen Space - Overlay` canvas). `RenderBoard`'s destroy loop left the held view at its *old, low* sibling index (skipped, not re-added), while the rebuild loop's `Instantiate`d survivors all landed at *new, higher* indices (`Instantiate` appends as last child) — so the held view silently drew underneath them.

**Fix attempt 2**: `RenderBoard` collected held children during the destroy pass and called `SetAsLastSibling()` on each *after* the rebuild loop finished, every call — not just once at `BeginHold` — since the rebuild loop re-appended survivors with fresh sibling indices on every refresh a hold spanned, so a one-time reorder wouldn't have survived the next refresh. Position (`ignoreLayout`) and draw order (`SetAsLastSibling`) were treated as independent fixes for independent mechanisms that happened to share the same root symptom (a stale sibling index) — fixing one did not fix the other, and both were needed at the time.

Both fixes were playtest-confirmed correct **in isolation** — re-tested against a mid-row exactly-lethal hit for both Fire and Arcane: burst rendered at the correct position, and rendered on top of the surviving siblings, not behind them.

### Bug 3 — surviving minions reflowed during the held sequence

Combining the two fixes above exposed a third bug: `ignoreLayout = true` removed the held view from the `HorizontalLayoutGroup`'s participant count entirely, not just from having its own position overridden — so with one fewer child counted, the *surviving* minions visibly reflowed/shifted into the space that would otherwise still include the held view's slot, instead of staying put during the held sequence.

Investigation showed this wasn't fixable by adjusting `ignoreLayout` further — the group had to keep counting the held view for the survivors' positions to stay put at all. But that created a direct conflict with the standing draw-order fix: `SetAsLastSibling` and "stay a counted participant at the correct *relative* slot" both wanted to control the same single sibling-index value for two unrelated jobs (layout order vs. draw order), and only one could win it at a time.

**Root cause, in hindsight, across all three bugs**: sibling index was being used as the sole channel for two independent concerns (board position and render order) that only coincided by accident in this project's flat `HorizontalLayoutGroup` + single `Screen Space - Overlay` canvas setup — every fix attempt that left this shared-channel assumption in place just moved the collision to a different symptom.

### Final fix — two independent channels, one per concern

- **Position**: `MinionView.BeginHold`/`EndHold` no longer touch `LayoutElement.ignoreLayout` at all — the held view stays a normal, counted `HorizontalLayoutGroup` participant, same as any live minion. `BoardDisplay.RenderBoard` captures each held child's sibling index *before* its destroy/instantiate pass touches the hierarchy, then — after instantiating fresh survivor views (which `Instantiate` always appends as new last children) — rebuilds the full sibling order as a merge: survivors that belonged before the held view's pinned index keep their relative order first, the held view is reinserted at exactly that pinned index, then the remaining survivors follow. This works because `MinionView`'s `LayoutElement` already carries a fixed, content-independent `PreferredWidth`/`PreferredHeight` (160×220) rather than deriving size from live text/artwork, and `BoardPanel`/`OpponentBoardPanel`'s `HorizontalLayoutGroup` has `ChildForceExpand` off with `ChildControlWidth/Height` on — so with a stable participant count, stable per-child size, and the held view restored to its original relative position, the row's total preferred width and every slot's computed position are byte-identical to the pre-death arrangement; survivors don't move at all.
- **Draw order**: sibling index no longer has any draw-order responsibility. `MinionView` now lazily adds (or reuses) a `Canvas` component on itself and toggles `overrideSorting`/`sortingOrder` in `BeginHold`/`EndHold` (mirroring the existing lazy-`GetComponent` pattern the old `LayoutElement` reference used to follow) — this renders the held view on top of its siblings via Unity's canvas-sorting system, completely independent of where it sits in the sibling list. `RenderBoard` no longer calls `SetAsLastSibling()` anywhere.

**Playtest-confirmed**: 3-minion board, exactly-lethal spell on the middle minion — both survivors' `RectTransform.anchoredPosition` logged identical across every `RenderBoard` call spanning the hold (temporary debug logging, added for verification and stripped once confirmed), held minion stayed frozen in its correct middle slot, burst rendered on top, then it disappeared cleanly with no post-death reflow glitch.

**Applies to the future `CardView`/`HandDisplay` hold** (Constraint 15, Next Steps 17): `HandPanel`/`OpponentHandPanel` also carry a `HorizontalLayoutGroup`, so that implementation should use this same two-channel pattern (counted participant + pinned sibling index for position, a local `overrideSorting` `Canvas` for draw order) from the start, not `ignoreLayout`/`SetAsLastSibling`.

Next Steps 18 step 3 (Arcane) is now fully complete — position, draw order, and layout stability are all playtest-confirmed with no open caveats.

## Lessons Learned / Gotchas

### Assembly definitions (.asmdef)
- Circular references are rejected — keep dependency direction one-way.
- An asmdef's real identity is its **Name** field (Inspector), not its filename.
- `CS0246` can mean either a missing asmdef reference OR a missing `using`.
- Cross-assembly type usage needs BOTH the `using` directive AND an explicit **Assembly Definition Reference**.

### Unity Editor / UI basics
- Script filename must exactly match its class name. Scene changes aren't saved until `Ctrl+S`.
- For stretch-anchored panels, reposition via Rect Transform `Pos Y`/`Left`/`Right`/`Height`, not free dragging.
- A circular gizmo appearing unexpectedly in Scene view is likely just the `Global Light 2D` gizmo — editor-only.
- Editing a runtime `(Clone)` GameObject in Play mode is temporary — use Prefab Edit Mode for permanent changes.
- **An empty/unassigned Inspector field for a listener-style hookup fails silently.** This is the single most repeated bug class in this project.
- Editing a TMP label's `Text Input` box requires clicking in, changing text, then clicking away to commit.
- `CS0102` after a manual paste-in usually means a duplicated field/header block — this is why full-file pastes are standard in chat sessions.
- A script field needing a component on the *same* GameObject: drag that GameObject onto its own field, Unity finds the matching component.
- A scene GameObject can accidentally become a prefab instance (showing `Prefab`/`Overrides`/`Select`/`Open` at the top of its Inspector) if it's ever dragged into the Project window. For a one-off bootstrapper never meant to be reused (like `EffectTester`), fix via right-click → **Prefab → Unpack Completely**, then delete the orphaned prefab asset.
- `UnityEngine.Random` can produce the same first result across rapid consecutive Play-mode restarts — a seeding quirk, not a logic bug. Add an explicit `Random.InitState(...)` before the pick.
- A full-screen background `Image` should have `Raycast Target` unchecked **proactively** when created, not fixed reactively after discovering it blocks clicks. Treat as the default habit for any purely-decorative `Image`.

### Code structure / design
- **Why `Minion` reference identity is safe — the full chain.** `List<Minion>.Contains()` resolves to reference equality (`Minion` is a plain class with no `Equals`/`GetHashCode`/`operator==` override), and that is safe here because minions are never copied: `new Minion(...)` appears exactly once in the codebase (`PlayerHand`), `Board.GetTauntMinions` returns a `FindAll` (new list, same element references), `BoardMinions` is only ever `Add`ed to and `RemoveAll`ed from, and the reference survives intact all the way through `RenderBoard` → `SetMinion` → the click closure → `new Target(minion)`. `Board.GetOwnerOf` (session 28) relies on the same property. **`CardData` is the opposite** — `BuildDeck` adds the same asset reference multiple times, so `Hand.Contains(card)`, `Hand.Remove(card)` and the `HashSet<CardData> mulliganSelections` cannot tell duplicates apart.
- `ScriptableObject`-based cards support "multiple copies in a deck" via repeated list references — no asset duplication. **But** see the identity caveat above.
- Use in-place Fisher-Yates for shuffling a `List<T>`.
- A boolean flag on the data itself (`CardData.targetsSelf`) is the right way to encode "who does this affect."
- A temporary/this-turn-only stat bonus needs no explicit expiry if it modifies a field some other system already resets unconditionally each cycle.
- When a UI component needs two distinct interaction modes sharing most setup, pull the shared parts into a private helper and give each mode its own public entry point, rather than a mode-flag parameter on one method.
- A "confirm/complete" boolean guard flag checked at the top of interactive handlers is a simple way to gate a whole phase without a full state machine — appropriate at small scale, worth revisiting as a real state machine if more phases get added.
- When adding a toggleable alternate mode (like `manualControlMode`) to code with implicit assumptions baked in (like "only Player One's hand is ever clickable, so no one checks whose turn it is"), audit those assumptions explicitly — new modes are a good forcing function for surfacing hidden coupling. *(Session 28 found Hero Power was still carrying exactly this bug, a session after the mode was added.)*
- **Deck design**: Hearthstone's real rule is many unique cards each capped at ~2 copies, not few unique cards with many copies. Preserve that shape (add `CardData` assets, don't raise `copiesPerCard`). Because `BuildDeck()` scales to any pool size without code changes, growing the pool is content work, not engineering.
- **Moving a check changes more than the check.** Relocating the Taunt guard from `OnMinionClicked`/`OnFaceClicked` (which `return`ed early) into `ResolveAttack` (which unconditionally cleared `selectedAttacker`) silently changed rejection behaviour. The logic was identical; the surrounding control flow was not. When lifting a guard into another method, check what the *new* location does after the guard.
- **Write in one tool, review in the other.** The chat workflow wrote the session 27 refactor and introduced a regression it didn't notice; Claude Code caught it, along with a missed file and four smaller issues. Scoping the review prompt to *what actually changed* made the findings much more targeted. Keep the "report findings before fixing anything" instruction — it makes the fix order a deliberate decision rather than an automatic one.
- **Documentation written about code the writer cannot read decays silently — audit it against the source periodically, in both directions.** The session 28 audit found four wrong rows, three of them written by a chat session with no filesystem access, plus a fabricated asset-name typo that survived several passes and generated a standing to-do item. It also found six hardcoded references in Hero Power where the fix prompt — written from the documentation — had named four. **A fix list derived from documentation is incomplete by default.** Every earlier pass had only checked documented→code; nobody had ever checked code→documented, which is where the unrecorded behaviour was hiding.

### `CardInstance` — the root fix for `CardData` reference identity (2026-09-06)

Two "copies" of a card were always the same `CardData` `ScriptableObject` reference (`BuildDeck` adds it `copiesPerCard` times), which kept producing scoped bugs anywhere code needed to tell two copies apart — `Hand.Contains`/`Remove` were blind to it. This had already surfaced twice before as separately-patched symptoms, never the root cause: session 31's spell-targeting pending-selection state (fixed by tracking hand-index instead, the old Constraint 17, removed with the click flow it served) and the `MulliganController` selection bug (fixed by switching to `HashSet<CardView>`, see the mulligan `CardView`-instance fix entry above).

**The root fix**: `CardInstance` (`Scripts/Cards/CardInstance.cs`), a plain C# wrapper (`public CardData Data`) with no `Equals`/`GetHashCode` override, so two instances wrapping the same duplicate `CardData` are distinct under default reference equality. `PlayerHand.Hand`/`.Deck` became `List<CardInstance>`, with the wrap happening exactly once, at `PlayerHand`'s constructor and `AddCardToHand` — every downstream consumer (`HandDisplay`, `CardView`, `CardDragResolver`, `MulliganController`, `AIController`) now reads card data through `.Data`. `EffectTester` needed zero changes, since `cardPool`/`coinCard`/`BuildDeck` stay `CardData` outside that boundary. Chosen over two alternatives: index-based tracking (the exact mechanism just removed, fragile under `Remove`/`Shuffle`/refresh) and cloning the `CardData` asset per copy (turns shared, authored data into throwaway `Object`s needing explicit `Destroy` lifecycle — fights the precedent `Minion` already set of wrapping shared stats in a plain class rather than cloning the asset). The `MulliganController` `HashSet<CardView>` workaround was removed as part of this fix, since `CardInstance` gives duplicates real identity directly — no further need for the `CardView`-as-identity-proxy indirection.

**Playtest-confirmed, all four planned cases**: two copies of the same card (Arcane Bolt) mulliganed together, both replaced, neither reappeared; drag-and-play with duplicates, one played, the other stayed in hand and remained playable; a full AI turn with duplicates in hand, completing cleanly via the AI-bypass path; a full human-vs-AI match smoke test, rendering/mana/effects all correct throughout. Preceded by a compile-time mechanism proof (a temporary `[MECH-PROOF]` log in `PlayerHand.MulliganCards` showing distinct instance hashes for duplicate copies, since removed) and a staged compile-verify propagation through `HandDisplay` → `CardView` → `CardDragResolver` → `MulliganController` → `AIController`. Full mechanism detail is kept in `PROJECT_STATUS.md`'s Known Issues section, since it documents an architecture decision still worth reading in full rather than pure session narrative.

## Board visual overhaul — phase 1, the fanning hand, opponent hand face-down step 1, and opponent hand fanning step A (2026-09-07)

Three commits, three playtest checkpoints, one feature: making the board *look* like Hearthstone. No game logic changed in any of it. The whole thing was planned up front as a single investigation before any code was written, specifically because the fanning hand touches drag-to-play and mulligan — the two things most at risk — and the plan deliberately ordered the work so the riskiest thing could be proven before anything was layered on top of it. See `PROJECT_STATUS.md` Next Steps 19 for current state, Constraints 28 and 29 for the durable rules, and Verification Status for the three playtest gates.

### Phase 1 — layout (commit `f5c8701`)

Scene-only, no script edits. `HandPanel`/`OpponentHandPanel` repositioned to hang off the bottom/top screen edges with `Raycast Target` disabled on both, and both `FaceView` portraits recentred top/bottom with their avatars centred. Two things fell out of this beyond the visual change.

First, disabling `Raycast Target` on the hand panels is what lets a drop pass *through* the hand to the board beneath — the panels had full-width transparent `Image`s acting as invisible blockers. Worth noting the asymmetry with the boards: `BoardDisplay.EnsureRaycastCatcher` deliberately *adds* exactly such an `Image` to `boardPanel`/`opponentBoardPanel` (Constraint 18), because empty board space needs to be hittable. Same component, opposite requirement, for two panels that sit on top of each other — the hand needs to be transparent to drops, the board needs to catch them.

Second, recentring the portraits gave `OpponentAvatarImage` point anchors, which fixed the long-standing stretch-anchor exposure (old Next Steps 10 and its Known Issue) as a side effect rather than as a targeted fix. Both avatars are now point-anchored, so the `FaceView` idle-animation base-scale capture no longer depends on a resolved parent rect for either of them — the exposure is gone at the root, not merely unreachable as it was before.

The commit also carried an unrelated one-line correction: `SpellAnimationSequencer.travelDuration` had a leftover debug value of `3` (a deliberate slow-down from an earlier spell-animation playtest) sitting uncommitted in the scene; the correct value is `0.35`. Caught during the pre-commit diff review rather than committed blind, and called out explicitly in the commit body instead of being folded into the layout message — the diff contained something the commit message didn't describe, which is exactly the case where saying so is cheaper than someone finding it later.

### The investigation that preceded the fanning work

The fanning hand was investigated in full before a line was written, because it replaces `HandPanel`'s `HorizontalLayoutGroup` and therefore touches how every hand card is positioned — with drag-to-play and mulligan both downstream of that. Several of the findings are now Constraints 28 and 29; three more are worth recording because they turned out to be **non**-problems, and knowing that is what allowed the work to proceed quickly:

- **Drop resolution never reads a card's transform.** `CardDragResolver.ResolveCardDrag` works entirely off `EventSystem.current.RaycastAll` at the *pointer* position and classifies hits by component type and transform ancestry. Rotating and overlapping the cards cannot affect it. The only transform read in the whole path is a `Vector3` world-position snapshot for the spell travel animation's start point, which stays correct for a rotated card.
- **Rotated cards hit-test correctly.** `RectTransformUtility.RectangleContainsScreenPoint` works off world corners, so a Z-rotated card's hit region is the rotated rectangle. The related hazard is `ignoreReversedGraphics` (on, by default, on the `GraphicRaycaster`): pure Z rotation keeps the graphic's normal facing the camera, but an X/Y rotation or a negative scale would flip it and silently drop the card from raycast results — which is why `HandFanLayout` is Z-only and never writes a negative scale.
- **A drag is latched at press.** `pointerDrag` is set at pointer-down and every subsequent `OnDrag`/`OnEndDrag` goes to that object regardless of what moves underneath. Cards reflowing, neighbours spreading, sibling order changing — none of it can hand a drag to a different card mid-gesture. Drag is structurally safe against relayout.

Also checked and confirmed: **mulligan is fully isolated**. `MulliganPanel` is a separate GameObject with its own `HorizontalLayoutGroup`, and `MulliganController` never instantiates into `handPanel` — the two only share screen *position*, which is why `BeginNewGame` blanks the hand with `RenderHand(null)` during mulligan. So fanning `HandPanel` could not affect the mulligan layout. The one real coupling is the **shared `CardView` prefab**, which is what made `CardHoverFan`'s self-disable guard a requirement rather than a nicety.

### Fanning step 1 — static arc (commit `f17a79f`)

`HandFanLayout` (new) on `HandPanel`, `HorizontalLayoutGroup` disabled, `RenderHand` collecting views into an explicit list, and the drag-ghost rotation/scale reset in `CardView.OnBeginDrag`.

The ghost reset is the piece worth remembering, because it was a *predicted* break rather than a discovered one: `Instantiate(original, parent)` keeps the source's local rotation and scale relative to the new parent, so the moment the cards acquired an arc angle the ghost would have been dragged around tilted. It was invisible before the fan existed only because rotation had always been identity. Finding it during planning rather than during the playtest is the concrete payoff of having investigated the drag path in full first.

The explicit `List<CardView>` (rather than letting the layout walk `handPanel`'s children) exists because `Destroy()` is deferred to end-of-frame: partway through `RenderHand` the panel holds both the outgoing pending-destroy cards and the new ones, so a child-walking layout would fan the wrong count for a frame. It also gave the layout an index channel independent of sibling index, which is what step 2's draw-order handling then depended on (Constraint 28).

**The full drag-to-play gate was run at this step, deliberately before any hover behaviour existed** — that split was the entire point of the step ordering. If drag had broken, the cause could only have been the arc itself.

### Fanning step 2 — hover-lift (commit `5cef62d`)

`CardHoverFan` (new) on the `CardView` prefab: a pure reporter that forwards pointer enter/exit and drag begin/end to the parent `HandFanLayout` and holds no layout maths of its own. The hovered card lifts, straightens to upright, scales up, and rises to last sibling for draw order.

**The self-disable guard is the load-bearing part of this component.** `OnEnable` looks for a `HandFanLayout` on a parent and sets `enabled = false` if there isn't one, which makes it a complete no-op rather than a guarded one (`ExecuteEvents` skips components failing `isActiveAndEnabled`). It covers two callers of the same shared prefab that must not gain hover behaviour: mulligan cards, instantiated into `MulliganPanel`, and the drag ghost, which `CardView` clones into the root `Canvas`. Without it, mulligan cards would have started lifting on hover.

One pre-existing latent conflict was resolved rather than worked around: the prefab `Button`'s `ColorTint` transition wrote the same `cardBackground.color` that `UpdateMulliganVisual()` sets directly for mulligan selection. It had always been there and had always been invisible; hover work would have made it visible. `Transition` set to `None`, and the mulligan toggle's greying was explicitly re-confirmed in the same playtest.

Two implementation choices worth carrying forward. Targets are **recomputed every frame in `Update` rather than cached**, so a hover change simply redirects the running lerp instead of needing an explicit recompute call — that is what makes rapid pointer sweeps interruption-safe, and it was confirmed under a deliberate fast-sweep test. And `ApplyLayout` **snaps** rather than eases, because a rebuild's cards are new objects still sitting at the prefab origin; easing there would have animated the entire hand in from the centre on every draw and every card played.

An anticipated failure mode that did **not** materialise, recorded because step 3 will meet it again: lifting the hovered card can move it out from under the pointer, producing an exit → return → enter oscillation. At `liftHeight` 60 against `hoverScale` 1.15 the card's bottom edge nets ~43px upward, so the risk was real enough to test for explicitly — and it did not appear. Step 3's neighbour-spread reintroduces the same failure mode on the horizontal axis, which is where the exit hysteresis deferred from step 2 is expected to earn its place.

A separate false alarm worth recording: an apparent vertical-stacking of the hand was investigated and turned out to be a Play-mode-editing artifact — a fresh untouched session renders a single clean fan. Worth knowing that this project's live-Editor workflow can produce layout artifacts that look like real bugs.

### Fanning step 3 — neighbour-spread, and the fanning hand's completion

`HandFanLayout` gained the last piece: hovering a card now pushes the cards near it sideways to open a gap, using a distance-based falloff (`spreadAmount`/`spreadRange`) that zeroes out beyond the configured range so distant cards keep their plain arc slot. This closes the fanning hand entirely — steps 1 (static arc), 2 (hover-lift), and 3 (neighbour-spread) are all playtest-confirmed.

**The edge-safety question turned out to already be answered by an existing constraint.** The worry going in was that spread might push outer cards off-screen at large hand sizes (7–10 cards). But `spread` (the arc's total width) is `Mathf.Min(maxTotalWidth, n*perCardStep)` — already capped independent of `n` — so the maximum possible offset with spread added, `spread/2 + spreadAmount`, is a *fixed* bound regardless of hand size, not something that grows and needs scaling down as hand count rises. A clamp to that bound was added as an explicit safety net, but the real answer is that the existing `maxTotalWidth` cap already made the failure mode structurally impossible. Playtest at 7–10 cards confirmed no off-screen pushes.

**The oscillation risk flagged at the end of step 2 materialised in exactly the predicted shape, on the predicted axis.** Step 2's lift never produced the exit → return → enter loop on the vertical axis; spread reintroduces the same shape on the horizontal one, because a neighbour sliding sideways can move out from under a pointer that never moved, firing a genuine `OnPointerExit` for the *hovered* card. Left alone, that exit would clear hover, which moves the neighbour back, which re-enters the pointer, which re-triggers the spread — a loop driven entirely by the layout's own motion. The fix (now **Constraint 30**) is exit hysteresis against the hovered card's *live* rect: `ClearHovered` takes the `PointerEventData`, converts the pointer position into the hovered card's current `RectTransform` local space (already reflecting whatever lift/scale/spread `Update` applied this frame), and only actually clears hover once the pointer is outside that rect padded by a margin (`exitHysteresisPadding`, 24 units). An exit that lands inside the padded rect is treated as noise from the layout's own motion, not a real departure. Playtest at a slow hover directly on the boundary between two adjacent cards confirmed no oscillation.

**`RestoreSiblingOrder()` was made lazy, pre-emptively rather than reactively.** Step 2 called it on every hover exit; step 3's neighbour movement was expected to make exits fire more often during a sweep, which could have turned an occasional draw-order pop into a constant one. Rather than wait to see if it was actually a problem, the exit path now just sets a pending flag and a short timer (`restoreSiblingOrderDelay`, 0.12s) that `Update` checks — the restore fires once nothing has been hovered for that long, and a new hover before then cancels it. `SetDragActive(true)` still restores immediately, since a drag starting is a discrete event rather than something a sweep produces repeatedly.

Full gate playtest-confirmed: smooth spread-open/settle-closed on a sweep; no off-screen cards at 7–10 cards; no oscillation at the adjacent-card boundary; dragging from a hovered/spread card still resolves the play; playing a card while neighbours are spread settles the hand cleanly to the new count; mulligan and the opponent hand both unaffected, as with steps 1 and 2.

### Opponent hand face-down, step 1 — logic and wiring (2026-09-07)

A planning pass preceded this one, deliberately, because of a real design trap: `OpponentHandPanel`/`opponentHandDisplay` looks like "the opponent's hand" but is actually dual-purpose — the AI's genuinely-hidden hand when `manualControlMode` is off, and a fully human-playable hand (draggable, via `CardDragResolver.CanPlayerTwoDrag`) when Craig is manually driving Player Two. Concealing it unconditionally would have silently broken manual-control testing of Player Two, a capability already relied on throughout this project's playtest history.

Two design options were weighed before building: a face-down *mode* on the shared `CardView` prefab, or a separate lightweight back prefab. The separate-prefab route was rejected on a concrete, codebase-specific precedent: this project already had a real bug (Constraint 14) from two structurally-parallel view prefabs (`MinionView`/`CardView`) drifting out of size sync. A second back prefab would reintroduce exactly that failure mode, needing its `RectTransform`/`LayoutElement` manually kept identical to `CardView`'s forever. A face-down mode on the same `CardView` instance can't drift, since there's no second source of truth.

**Built**: `CardView.SetCard` gained a `faceDown` bool (default `false`), which — when true — skips `WriteCardText()` and calls a new `ShowFaceDown()` instead: hides `nameText`/`costText`/`statsText`/`artworkImage` and swaps `cardBackground` to a flat placeholder color (`faceDownColor`). Drag wiring was deliberately left untouched — `canDrag` already governs whether a drag can start at all, independent of what's drawn. `HandDisplay.RenderHand` gained a matching `Func<bool> faceDown` parameter, following the exact same predicate-injection pattern already used for `canDrag`, evaluated once per render (a hand is all-concealed or all-revealed together, never a per-card mix) and passed straight through to every `SetCard` call. Wired **only** at `EffectTester`'s opponent call site as `() => !manualControlMode`, mirroring `CanPlayerTwoDrag`'s own check — the player's own `handDisplay.RenderHand` call never passes it, so that hand is structurally unaffected regardless of what the opponent panel does. This dual-purpose-panel trap is now **Constraint 31**.

One accepted, deliberately-not-fixed gap: `manualControlMode` is a bare Inspector bool with no `Update()` poll behind it (matching `BoardDisplay`'s pre-existing `showAttackEligibility: ... && manualControlMode`, which has the identical lag), so toggling it doesn't instantly re-render the hand — the face state only updates on the next natural `RefreshHandDisplay()` call. Judged a fine one-refresh delay for a debug affordance rather than worth new per-frame polling code.

**Playtest-confirmed, full gate**: opponent hand shows the correct count of backs when AI-controlled; toggling `manualControlMode` on reveals the real cards on the next refresh and Player Two's hand is playable exactly as before (Goblin dragged and played successfully under manual control); the player's own hand — faces, fan, hover, drag — completely unaffected; mulligan cards stay face-up and toggleable (confirmed explicitly despite sharing the same prefab, since `SetCardForMulligan` is a fully separate method that never passes `faceDown`); backs sit correctly in `OpponentHandPanel`'s flat `HorizontalLayoutGroup` row, same size as face cards since it's the same prefab. **Step 2 (a real back design — border/motif, not just a flat color) is deliberately deferred** — this step was logic and wiring only.

### Opponent hand fanning, step A — mirrored static fan (2026-09-07)

A second planning pass preceded this one, since it touches the fanning system directly and adds a runtime-mode twist: the opponent hand should switch between a static fan of backs (AI-controlled) and a fully interactive fan (Craig piloting Player Two under `manualControlMode`) — the same dual-purpose-panel shape as Constraint 31, now applied to the fan itself rather than just face visibility.

**The mirroring math turned out to be a single sign flip, not a parallel formula.** `ApplyToCard`'s y-parabola (`-arcDrop * (offset*2)²`) and tilt (`-offset*2*maxTiltDegrees`) both already encode "hangs down, centre highest, edges dip low, tilted outward" purely through the sign of `offset` — there was no existing dependency on which panel it's running against. A true vertical mirror needed both flipped together, not just y: a reflection across a horizontal axis inverts rotation sense as well as position, so flipping only y would have produced a fan curving the wrong way relative to its own tilt. The fix multiplies the already-fully-computed `y` and `angle` (lift included, since it's folded into `y` before the flip) by a single `sign` derived from a new `invertVertical` bool — `x` is untouched, since horizontal card ordering never differs between the two panels.

**The static-vs-interactive switch needed no new "static mode" code at all**, because it already existed by omission: `Update()`'s `hoveredIndex` is `-1` whenever `hoveredView` is `null`, and that code path *is* the plain, unlifted, unspread arc. Gating `SetHovered`/`ClearHovered`/`SetDragActive` behind a new `interactionEnabled` bool (early-return when `false`) is sufficient to guarantee `hoveredView` can never be set, which is sufficient to guarantee the static path runs forever. `CardHoverFan` needed zero changes — it still just forwards events to `HandFanLayout`, which now sometimes chooses not to act on them.

**Built**: `HandFanLayout.ApplyLayout(List<CardView>, bool interactive = true)` stores the flag into `interactionEnabled`; `HandDisplay.RenderHand` gained a matching `Func<bool> fanInteractive = null` parameter (same predicate-injection pattern as `faceDown`, evaluated once per render, `null` meaning "always interactive" so the player's call site is unaffected). `OpponentHandPanel` got its own `HandFanLayout` component instance (`HorizontalLayoutGroup` disabled, not deleted — Constraint 29) with `invertVertical = true` and the same arc/tilt magnitude as `HandPanel`'s instance, since the sign flip handles direction and there was no reason yet to expect the opponent needs different depth. `EffectTester`'s opponent call site wires `fanInteractive` to a hardcoded `() => false` for this step — deliberately not yet `manualControlMode`, which is step B.

One design note carried forward rather than resolved: `faceDown` (`() => !manualControlMode`) and `fanInteractive` (eventually `() => manualControlMode`) are two independent wirings of the same underlying flag, not one shared source. Low risk today since both are live reads of the same field at the same call site, but flagged in `HandDisplay.cs`'s own doc comment as a "keep both in sync" note, the same shape of risk `Board.GetTauntMinions`'s two call sites already document under Constraint 2.

**Playtest-confirmed**: opponent hand renders as a static mirrored fan — arcs upward toward the board, centre card lowest, outer cards rising and tilted outward the opposite way from the player's downward fan, correct card count, confirmed visually side-by-side with the player's hand as a clean vertical mirror. Sweeping the pointer across it produces zero response (no lift, no spread, no draw-order change). Player's own hand — faces, fan, hover, spread, drag — and mulligan both fully unaffected.

### Working note — the live Editor and who edits the scene

Every scene and prefab change in this block was made by Craig in the Inspector, not written to the `.unity`/`.prefab` files from the coding session, because the Unity Editor was open on the project throughout (`Temp/UnityLockfile` present). The Editor holds the open scene in memory and rewrites it on its next save, so disk-side edits from outside would be silently clobbered — and worse, a playtest could run against the unmodified in-memory scene while the disk looked correct. Splitting it as "Claude writes the scripts, Craig does the Inspector wiring" avoided that entirely, and the scripts were compile-verified with `dotnet build UI.csproj` in the meantime. Note the related `.csproj` gotcha from Constraint 13 recurred as expected: a brand-new script needs a temporary manual `<Compile Include>` entry before `dotnet build` sees it, until Unity regenerates the (gitignored) project file.
