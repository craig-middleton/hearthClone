## Project Goal
Hearthstone-style card game in Unity, single-player vs AI, C# with data-driven cards/effects (ScriptableObjects). Ubuntu, Unity + VS Code, Git/GitHub with LFS for art/audio. Repo: `github.com/craig-middleton/hearthClone`.

**Unity 6.5 (60000.5.2f1).** TextMeshPro for all UI text, never legacy `UnityEngine.UI.Text`.

## Architecture
- Folders under `Assets/_Project/`: Scripts, ScriptableObjects, Prefabs, Art, Scenes. Cards are data-driven — they reference reusable `CardEffect` assets.
- **Assembly Definitions** enforce one-way flow: `Core` (no deps) ← `Effects` (Core) ← `Cards` (Core, Effects) ← `AI` (Core, Cards, Effects) ← `UI` (Core, Cards, Effects, **AI**, TMP). `Effects` must NOT reference `Cards`; `UI` references `AI` because `EffectTester` constructs `AIController`.
- **Keep `Core` generic and unaware of `CardData`.** AI-ness isn't a flag on `Player`.

### Design principles in force
Named only; reasoning and worked examples in HISTORY under Lessons Learned.
- **Rules live at the chokepoint** · **a rule is only centralised if its *inputs* are too** (`TryAttack` derives the defender rather than accepting it) · **guard *before* you instantiate** · **hiding something from the view doesn't remove it from state** · **reference identity: `Minion` was always safe by design; `CardData` was not, until `CardInstance` (this session) gave hand/deck cards the same real per-instance identity** · **"two of something" is a second *instance***, not code juggling two lists.

2. **`Board.GetTauntMinions` has two call sites**: `Combat.TryAttack` (the rule) and `AIController` (its targeting heuristic). The *rule* lives in one place, the *lookup* in two — **changing it means checking both.**
3. **`Board.GetOwnerOf(Minion)` returns null** when the minion is on neither board. Callers must handle null.
4. **`Combat.TryAttack` guard order**: null attacker/target → null board → malformed `Target` → derive defender → attacker `IsDead` → target minion `IsDead` → defender null → own-side → Taunt → `CanAttack`. 5. **Accepted gap in `Combat.TryAttack`**: an attacker on neither board passes the own-side check (`GetOwnerOf(attacker)` is null, `defender` isn't). `attacker.IsDead` covers the realistic case; the rest needs a caller fabricating an off-board `Minion`. Deliberately unguarded.

12. **Older `CardData` assets physically omit later-added fields.**
    - **State**: `hasTaunt` is absent from **14 of the 16** assets (present only on `TestCard_Shieldbearer` as `1` and `TestCard_Goblin` as `0`). `artwork` and `description` are present on all 16. (`targetsSelf` used to be absent from 4 assets here as an example of this hazard — it no longer exists, having been renamed to `targetRequirement` in session 31 and hand-written into every asset that needed it; see Card Pool.)
    - **Mechanism**: adding a field to `CardData.cs` does **not** rewrite existing assets. An asset's YAML is written only when Unity saves *that asset* — an Inspector edit, a scripted write, or a forced re-serialize — and until then it keeps whatever field set it had when last written. Missing fields fall back to the C# initializer at load. Git shows it cleanly: `targetsSelf` landed in `48e9d98`, and the ten-card batch created two commits later (`8963670`) has it; `hasTaunt` landed in `b2c217f`, five commits *after* that batch, so every asset lacks it except the two re-saved since. The clincher is `de18de0`, where assigning Goblin's artwork wrote **both** `artwork:` and `hasTaunt: 0` into the file in one diff — nobody touched Goblin's Taunt checkbox; the whole asset was simply re-serialized.
    - ✅ **New assets are fine.** A card asset created *after* a field exists gets that field written at creation — which is exactly why the ten-card batch has `targetsSelf`. The hazard is confined to assets that already exist when the field is added.
    - **Hazards**: grepping the assets for a field name misses most cards (`grep hasTaunt` returns 2 of 16); and changing a field's initializer in `CardData.cs` silently flips every asset that omits the field, while leaving the explicitly-written ones alone.
    - **Remedy**: force re-serialization — `AssetDatabase.ForceReserializeAssets` on the `CardData` assets, or touching each one in the Inspector — which writes the omitted fields physically into every file. ⚠️ **Do this BEFORE changing any field's initializer, never after.** Afterwards the silent flip has already happened, and re-serializing only pins the wrong values in permanently.

14. **A child positioned with point anchors (`AnchorMin == AnchorMax`) and a fixed `SizeDelta` does NOT track its parent's actual resolved size** — its size is absolute, set once, independent of whatever `HorizontalLayoutGroup`/`VerticalLayoutGroup` later assigns the parent. `MinionView`'s `ArtworkImage` was point-anchored with `SizeDelta` hand-matched to the *design* size (160x220); under `BoardPanel`'s `HorizontalLayoutGroup` (`Control Child Size` on, no min width set on the `LayoutElement`), a board with enough minions to exceed the panel's width shrinks every `MinionView` root below 160x220 — but `ArtworkImage`, unaffected by the layout group (it's a grandchild, not a direct child), stayed at the fixed 160x220 and overflowed past the shrunk card. Invisible on minions with no artwork (`Image.enabled = false`), so only artwork-bearing minions (Goblin) appeared to render "bigger" than their neighbours, though the root `RectTransform` sizes were identical the whole time. **Fix**: `ArtworkImage` now uses stretch anchors (`AnchorMin {0,0}` / `AnchorMax {1,1}`, `SizeDelta {0,0}`) so it always exactly fills whatever size the root actually resolves to. **Any child meant to fill `MinionView` or `CardView`'s root must use stretch anchors, not point anchors with a size that merely matches today's design dimensions** — the design dimensions and the runtime-resolved size are only the same number by coincidence, not by construction.

16. **A lethal spell hit on a minion can destroy the target's `Transform` mid-animation — `SpellAnimationSequencer` must tolerate that, not assume the target survives.** Originally found via `EffectTester.ResolveSpell` (session 31, since removed — see Constraint 17); the same fix and same risk apply unchanged through `ResolveCardDrag` (session 32), which starts the travel coroutine (holding a live target `Transform`) *before* `AfterGameAction()` runs, identically; `AfterGameAction` calls `RemoveDeadMinions()` then `RefreshAll()` synchronously in the same frame, which destroys the dead minion's `MinionView` before the coroutine's next `yield` resumes — an exactly-lethal hit throws `MissingReferenceException` on the following frame's `targetView.position` read. **Fix**: `TravelAndReactRoutine` re-checks `targetView != null` every frame (Unity's overloaded operator correctly flags a destroyed-but-not-nulled `Object`) and falls back to the last position sampled before it died; the end-of-travel reaction call is skipped the same way if the target is gone. **Chosen over unconditionally snapshotting the target's position at cast time** (the same treatment already given the source side) because the target survives intact in the overwhelming majority of casts — only a lethal kill destroys it — and is deliberately tracked live so `FaceView`'s idle sway shows through during travel; an unconditional snapshot would silently kill that sway for every cast, not just lethal ones, to guard a one-frame-rare edge case. **Confirmed minion-only**: `FaceView` is never destroyed by a refresh (`RefreshFaceDisplay` only calls `SetPlayer()` on the existing instance), so a lethal face hit cannot hit this bug — playtest-confirmed, not assumed. **Superseded in part (this session) — see Constraint 22**: this constraint's `targetView != null` fallback machinery is still exactly correct and still runs unchanged, but its *consequence* changed. `MinionView`'s hold mechanism now keeps a lethally-hit minion's view alive (undestroyed) through the end of its spell-cast animation, so `targetView != null` at the impact check now reads **true** for a lethal hit too — meaning `PlayDamageReaction()` (the flash) **now fires on a killing blow**, where it was previously silently skipped by this exact null-check. That was never a documented *intended* behavior, just the accepted side effect of a fix that only guaranteed no-crash, not correct timing — the flash-on-lethal is a deliberate, confirmed improvement, not a regression of this constraint's fix. This constraint's core lesson (never assume a minion target survives to the end of travel) still stands as the reason the hold exists in the first place.

18. **`boardPanel`/`opponentBoardPanel` need a raycastable `Graphic` covering their full bounds, or `EventSystem.RaycastAll` returns zero hits over empty board space.** uGUI's graphic raycasting only hits GameObjects that carry a `Graphic` (`Image`, etc.) with `raycastTarget` on — a bare `RectTransform` panel used only as a layout container isn't hit-testable itself, regardless of what's visually rendered under it (in this case a separate, decorative `boardBackgroundImage`, not a child of either board panel). Drag-and-drop's `ResolveCardDrag` (Code Written So Far, `EffectTester.cs`) needs the board panels to register a hit for None/Self-target spells and minion summons dropped on open board space, not just on an existing `MinionView`/`FaceView` — those already had their own raycastable `Graphic` and were never affected. **Fix**: `BoardDisplay.Awake()` → `EnsureRaycastCatcher()` adds a fully transparent `Image` (`raycastTarget = true`, alpha 0) directly on `boardPanel`'s own GameObject, not a child — `RenderBoard()` destroys all *children* of `boardPanel` every refresh, so a child-based catcher would be destroyed and need re-adding every render; the panel's own GameObject survives refreshes untouched. Runs once per `BoardDisplay` instance, so both boards get it automatically with no scene/Inspector editing. **Any future feature adding another droppable/clickable zone must confirm that zone has a raycastable `Graphic` covering its full area, not just assume the visible art makes it hittable.** **Diagnostic note**: the bug first surfaced as an apparent Player-Two-only gating failure (dragging Player Two's own card produced total console silence), which led the investigation down a wiring/gating path before a `[DragDiag]` trace showed the callback firing correctly and rejecting on zone-recognition — the real bug was universal to both players and specific to empty board space, not to Player Two at all. **A reported symptom narrower than the actual bug is common**; testing the wider case (here: "does Player One's drop on empty board space also fail?") is what surfaced the true scope.

20. **Hand-editing Unity-generated `ProjectSettings/*.asset` YAML (e.g. `TagManager.asset`) is stricter and less forgiving than editing scene/prefab YAML, and fails silently.** Found adding the `UIParticles` layer for the spell-VFX plan's isolated `ParticleSystem` render test (Next Steps, spell VFX). Unity's asset parser is not a general-spec YAML parser — it expects the exact formatting it itself emits. Writing an empty layer slot as a bare `-` instead of Unity's own `- ` (dash **+ trailing space**) broke the parser's list-tracking state and cascaded into a full-file parse failure (`Parser Failure at line N: Expect ':' between key and value within mapping`, reported against an unrelated, untouched line further down the file — here, the `m_SortingLayers` block). The practical effect is much worse than a bad scene/prefab edit: **the entire settings file silently reverts to defaults** — no custom layers, tags, etc. — rather than failing to load just the one malformed object. **Exact failure signature, so this is recognized immediately next time instead of re-diagnosed from scratch:**
    - The edit "looks right" by inspection and even by `grep`/`cat` — the added value (e.g. the layer name) is genuinely present in the file.
    - The corresponding runtime lookup (`LayerMask.NameToLayer`, or the equivalent for whatever settings type) returns "not found" / default anyway.
    - **Restarting the Editor does NOT fix it** — ProjectSettings is only re-read on load, but the file itself is still malformed on disk, so every reload re-fails the same way.
    - **The Console shows no error.** The only place this surfaces is `Logs/Editor.log`, as a `Parser Failure` line — check that file, not the Console, not just the relevant Project Settings window (which only shows *fewer entries than expected*, with no error of its own, since it's reading whatever the parser fell back to).
    - **Remedy**: match Unity's own emitted formatting exactly, byte-for-byte, for the file type being touched — for `TagManager.asset` specifically, every empty layer slot is `- ` (dash, space, nothing else), never a bare `-`. When in doubt, diff a known-good copy of the same asset type rather than hand-formatting from memory.

22. **`MinionView`'s hold mechanism (`BeginHold`/`EndHold`/`IsHeld`) is the resolution of Constraint 15 — DONE, playtest-confirmed (this session) across lethal, non-lethal, and the combat-kill regression.** A counter-based (not bool, so overlapping holds can't clear each other early), TTL-bounded (`holdExpiresAt`, logged if a hold is ever swept by TTL instead of an explicit `EndHold()`) hold that `BoardDisplay.RenderBoard`'s destroy loop respects — a held child is skipped instead of destroyed. **Playtest checklist, all confirmed**: (1) combat kill — a minion killed in combat (never acquires a hold) still disappears exactly as instantly as before this session, zero regression from the unused-but-present machinery; (2) exactly-lethal spell hit — minion stays visible through the full travel + flash reaction + spell burst, *then* disappears, matching the fix's intent exactly; (3) non-lethal spell hit — unaffected, behaves as before. **Who may call `BeginHold`, and when it's safe**: only when the `Minion` a view represents has already been removed from the model (`Minion.IsDead` true, checked synchronously before any `yield`) — holding a still-*present* minion's view would make `RenderBoard`'s rebuild loop spawn a second, fresh view for the same still-modeled `Minion` while the held one lingers too, a visible on-screen duplicate. `SpellAnimationSequencer` is the first caller (Next Steps 18, step 2); `CardView`/`HandDisplay` are the intended next callers for lift/zoom and discard-off (Next Steps 17) — same mechanism, same rule about only holding what's actually gone from the model. **Whoever calls `BeginHold` owns calling `EndHold()` and explicitly `Destroy()`-ing the GameObject when done** — a held view is skipped on every future refresh until released, so nothing else will ever clean it up; the TTL is a safety net for a caller bug, not a substitute for this. See Constraint 16 for the resulting behavior change (flash-on-lethal now fires).
23. **A held view's board position and its draw order must use two independent mechanisms — sibling index cannot serve both at once.** `MinionView.BeginHold`/`EndHold` no longer touch `LayoutElement.ignoreLayout` — the held view stays a normal, counted `HorizontalLayoutGroup` participant, and `BoardDisplay.RenderBoard` pins its sibling index back to its pre-death slot on every refresh (merging survivors around it), so the row's computed layout never reflows. Draw order is handled separately: a lazily-added `Canvas` on the held view toggles `overrideSorting`/`sortingOrder` in `BeginHold`/`EndHold`, rendering it above its siblings via Unity's canvas-sorting system regardless of where it sits in the sibling list. **Why two channels**: this project's flat `HorizontalLayoutGroup` + single `Screen Space - Overlay` canvas setup makes sibling index double as both the layout group's position key and the de facto draw-order key — but they're unrelated concerns, and three sequential bugs (position, then draw order, then a layout-reflow regression) came from fix attempts that reused the same value for both. Playtest-confirmed (killing the middle minion of 3+ with an exactly-lethal spell leaves both survivors' positions unchanged throughout the sequence) — **Next Steps 18 step 3 (Arcane) is fully complete**, position/draw-order/layout-stability all playtest-confirmed with no open caveats. **Applies to the future `CardView`/`HandDisplay` hold** (Constraint 15, Next Steps 17) — `HandPanel`/`OpponentHandPanel` also carry a `HorizontalLayoutGroup`, so build that hold with this same two-channel pattern from the start. Full investigation (all three bugs, what each fix attempt broke, and why) is in PROJECT_HISTORY.md.
24. **A duration-based status flag must NOT be cleared unconditionally on the first per-turn reset call after it's set — that clears it before it ever blocks anything, giving zero effective duration instead of one full turn.** Found building the Frost mechanic (`Minion.IsFrozen`, Next Steps 18/Tier 2 — the project's first status-effect game logic). `TurnManager.ResetMinionsForNewTurn(player)` already fires at exactly the right moment — the start of the affected minion's controller's turn — so the turn-boundary call site itself was never wrong, confirmed by explicit review before implementing the fix. The bug was entirely inside `Minion.ResetForNewTurn()`: it cleared `IsFrozen` unconditionally on that very first call, which is the call that starts the turn the freeze is supposed to still be blocking. Net effect before the fix: a minion frozen on turn N was already unfrozen going into turn N+2 (its controller's very next turn) instead of staying frozen through it — playtest showed the minion attackable immediately after a single `EndTurn`. **Fix**: a second flag, `IsNewlyFrozen`, set alongside `IsFrozen` in `Freeze()`. `ResetForNewTurn()` only clears `IsFrozen` when `IsNewlyFrozen` is already `false` — the first reset call after freezing just consumes `IsNewlyFrozen` (sets it `false`) and leaves `IsFrozen` alone; only the *second* reset call for that controller actually clears it. Playtest-confirmed via an explicit four-turn trace (Verification Status), not just an end-state check — the original bug's end state (eventually unfrozen) looked correct and only the *timing* was wrong, which a same-day end-state check would have missed. **Applies to every future turn-duration effect** (e.g. a hypothetical "Silence for one turn") — any status meant to survive exactly one full turn of its target's controller needs this same consume-then-clear two-flag pattern; a single bool cleared unconditionally on the first `ResetForNewTurn()` call will always yield zero effective duration, not one turn, regardless of how correct the turn-boundary call site itself is.
25. **`UIParticleBurstRenderer` is a single shared instance used by both small point bursts (Fire/Arcane/Frost, via `ShowAt`) and board-wide region effects (Blizzard's sweep, via `ShowAtRegion`) — a region call that resizes/reframes it (display rect size, camera `orthographicSize`, render texture dimensions) leaves that state in place until something resets it.** Found building Blizzard's board-sweep VFX (Next Steps 18/AoE plan). Without an explicit reset, casting Blizzard and then any ordinary single-target spell in the same session would render that NEXT point-burst at board-region scale/aspect instead of its normal small dimensions — a real regression this session confirmed and fixed before it could ship, not a hypothetical. **Fix**: `ShowAt` unconditionally calls `RestorePointBurstFraming()` on every invocation, restoring size/orthographic-size/texture dimensions snapshotted once in `Awake()` — so every ordinary point-burst call self-heals regardless of what a prior `ShowAtRegion` call left behind, with no dependency on cleanup happening at the *end* of a sweep (which would be fragile if a sweep coroutine is ever interrupted). **Applies to any future third consumer of this renderer**: a new call site must either route through `ShowAt`/`ShowAtRegion` (inheriting the existing reset discipline) or, if it needs a third distinct framing mode, extend `RestorePointBurstFraming`'s snapshot/restore pattern rather than assuming the renderer starts each call in some default state — it doesn't; it starts in whatever state the *previous* caller left it. `ShowAtRegion` also exposes `LastRegionWorldWidth`/`LastRegionWorldHeight` (the world-space size of its most recent capture, at the same units-per-canvas-unit ratio used to set `orthographicSize`) — a future region-based effect should read these rather than re-deriving the conversion ratio itself, since the ratio is a private implementation detail of `ShowAtRegion`.

26. **A targeting restriction that must never be violated (e.g. "never heal the opponent's face") cannot be enforced only in `CardDragResolver` — `AIController.TakeTurn()` builds `Target` objects directly and calls `PlayerHand.PlayCard()` without going through the drag resolver at all.** Found building `HealEffect` (Nature spells, this session). `CardDragResolver`'s per-`TargetRequirement` gating (`Any`, `AnyMinion`, `Friendly`) is real but is a UI-layer convenience only — it improves human-player UX (rejecting an invalid drop instead of a silent no-op) and is trivially bypassed by any caller that doesn't route through it, which `AIController` already doesn't. **The only chokepoint both the human-drag and AI paths share is `PlayerHand.PlayCard` → `CardEffect.Execute`** (`Execute` now takes a `Player caster`, added this session specifically to make this enforcement possible — see Code Written So Far, `CardEffect.cs`). `HealEffect.Execute` enforces "never heal the opponent's face" itself (`target.TargetPlayer != null && target.TargetPlayer != caster` → no-op), independent of whatever `CardDragResolver`/`AIController` upstream did or didn't get right. **Verified, not just designed**: a temporary test harness forced `AIController`'s `Friendly` branch to `new Target(opponent)` (simulating exactly the kind of AI targeting bug this guard exists for) and ran a real AI turn — the `Execute`-level guard correctly blocked the heal and the opponent's health was unchanged, confirming the UI-layer gate is not load-bearing for correctness. **Any future effect with a hard targeting restriction (not just a UX nicety) must put the authoritative check in the effect's own `Execute`, using the `caster` parameter — a `CardDragResolver`/`TargetRequirement` gate alone is never sufficient**, exactly because the AI path exists and doesn't go through it. ✅ **RESOLVED (code refactor audit session) — the guard only covered the face half of this restriction.** `HealEffect.Execute` checked `target.TargetPlayer != caster` but had no equivalent check for `target.TargetMinion` ownership, meaning the minion half of "never heal the opponent" lived only in `CardDragResolver`'s `Friendly`-branch gating (a UI-layer convenience `AIController` bypasses, exactly the class of gap this constraint exists to prevent) — not exploitable in practice since neither live path ever constructs that Target, but a real gap in the stated rule. Fixed by adding `context.Board.GetOwnerOf(target.TargetMinion) != caster` alongside the existing face check, using the `GetOwnerOf` lookup Constraint 3 already documents. Compile-verified.

27. **Every persistent `MonoBehaviour` display component (`BoardDisplay`, `FaceView`, `HandDisplay`) only tears down and re-renders its content when explicitly called again — none of them self-clear on construction, because none of them get reconstructed. A restart (or any future "rebuild the game state" path) must explicitly call each one's refresh/clear method itself, or the previous game's rendered content just sits there untouched.** Found building the restart/new-game feature (Next Steps 13): `EffectTester.BeginNewGame()` rebuilds the entire *model* (`Player`, `Board`, `PlayerHand`, all four controllers) fresh on every call, but `boardDisplay`/`opponentBoardDisplay`/`faceView`/`opponentFaceView`/`handDisplay`/`opponentHandDisplay` are the *same* serialized `MonoBehaviour` instances across every game — restarting never destroys or reconstructs them, since they're wired once in the Inspector, not part of the composition root's object graph. Three real, separately-discovered instances of this same class of bug in one pass: (1) `BoardDisplay` never re-renders until something calls `RenderBoard()`, so a restart's mulligan screen showed the just-finished game's leftover `MinionView`s still standing on an otherwise-empty board — fixed by calling `RefreshBoardDisplay()` in `BeginNewGame()` before `ShowMulliganUI()`. (2) `FaceView.SetPlayer()` only rewrites HP/mana text when called, so the same restart showed the previous game's final HP/mana on both faces — fixed by calling `RefreshFaceDisplay()` at the same spot, for the identical reason. (3) `HandDisplay.RenderHand()` only destroys/rebuilds its children when called, so both `HandPanel` and `OpponentHandPanel` still held whatever `CardView`s the previous game's final `AfterGameAction()` had rendered — surfacing as a stray leftover card floating near the top of the screen (`OpponentHandPanel`, confirmed via its scene `RectTransform` anchored top-center) and extra overlapping card shapes behind the mulligan row (`HandPanel`, confirmed to share `MulliganPanel`'s exact screen footprint) — fixed by calling `RenderHand(null)` on both panels in `BeginNewGame()`, which reuses `RenderHand`'s own destroy-loop to clear without repopulating (deliberately not the new, correct hand — see `HandDisplay.cs` row for why that would just swap stale-duplicate cards for correct-content-duplicate cards in the same overlap). **Checklist for any future persistent display component this project adds**: does it own a "last rendered state" that only changes when explicitly told to? If so, whatever rebuilds the game's model (today: `BeginNewGame()`) must also explicitly call that component's refresh/clear method — it will not infer "the model changed" on its own, and a stale display bug from this class is easy to miss because nothing throws or logs a warning.

28. **Adding a nested `Canvas` (with `overrideSorting`) to a UI object silently removes it from raycast results — it is NOT a safe general way to raise draw order on anything that must stay interactive.** `Graphic.CacheCanvas()` resolves each graphic to its *nearest enabled `Canvas` ancestor*, and `GraphicRegistry` is keyed on exactly that canvas with no parent propagation (`GetRaycastableGraphicsForCanvas(canvas)` is an exact-match dictionary lookup). A root `GraphicRaycaster` therefore only ever sees graphics registered to *its own* canvas — the moment a child gains its own `Canvas`, its graphics re-register there and disappear from the root raycaster's results. The object still *renders* correctly, which is what makes this so hard to diagnose: it simply stops responding to hover, clicks and drags, with no error and nothing visibly wrong. **`MinionView.BeginHold` uses this pattern safely only because a held view is deliberately non-interactive** — `BeginHold` strips `button.onClick` listeners anyway, for the separate stale-`Minion` reason in Constraint 22. That is a coincidence of that use case, not a general endorsement of the pattern. If a view needs *both* raised draw order and working input, either add a `GraphicRaycaster` alongside the nested `Canvas`, or avoid the nested `Canvas` entirely. `HandFanLayout` takes the second route: arc slots come from an explicit list index, never `GetSiblingIndex()`, which frees sibling order to mean draw order alone — so hover can just call `SetAsLastSibling()`. This is Constraint 23's "two independent mechanisms" rule applied the other way round: there, layout owned sibling index and draw order needed its own channel; here, draw order owns sibling index and layout needed its own.
29. **A `LayoutGroup` must be DISABLED, not merely written over, before a custom script can position its children.** `LayoutGroup.SetChildAlongAxisWithScale` registers `Anchors` + `AnchoredPosition` (and, with `ChildControlWidth`/`ChildControlHeight` on, `SizeDelta`) in a `DrivenRectTransformTracker`, and force-writes `anchorMin = anchorMax = Vector2.up` on every child it lays out. Unity's canvas layout pass runs *after* `Update` and *before* render, so anything a custom script writes to `anchoredPosition` is clobbered in the same frame while the group is still enabled — the children snap back to the group's row every frame with nothing on screen explaining why. Disabling the component is the clean fix: `LayoutGroup.OnDisable` calls `m_Tracker.Clear()`, releasing the driven properties. **Disable rather than delete**, so the old behaviour stays one checkbox away. Two corollaries: (1) a custom layout must set `anchorMin`/`anchorMax`/`pivot` itself and must NOT trust the prefab's serialized values, since the group will have overwritten them to `(0,1)` on any child it ever laid out; (2) a custom layout that computes its own positions does **not** need `LayoutRebuilder.ForceRebuildLayoutImmediate` — that call exists in `MulliganController` only because a `HorizontalLayoutGroup` defers its position computation to the layout pass, and there is nothing deferred to force once the script does the maths itself. `HandFanLayout` on `HandPanel` is the first user of this; `MulliganPanel` and `OpponentHandPanel` deliberately keep their groups enabled and are unaffected.
30. **When a script moves a UI element under a stationary pointer (not just moving the pointer over a stationary element), the standard `IPointerExitHandler` exit event is not sufficient on its own to decide whether hover should actually end — check the element's CURRENT (post-move) on-screen rect, padded by a margin, before honouring the exit.** Found building fanning step 3 (neighbour-spread, Next Steps 19): once hovering a card pushes its neighbours sideways to open a gap, a neighbour can slide out from under a pointer that never moved, which fires a genuine `OnPointerExit` for the hovered card — and if that exit is honoured immediately, clearing hover moves the neighbour back, which re-enters the pointer, re-triggering the spread, which pushes it out again — an oscillation loop entirely driven by the layout's own motion, not by anything the player did. **Fix**: `HandFanLayout.ClearHovered` takes the `PointerEventData` and, before clearing, converts the pointer's screen position into the hovered card's own `RectTransform` local space via `RectTransformUtility.ScreenPointToLocalPointInRectangle` — using the card's **live** transform, i.e. already reflecting whatever lift/scale/spread `Update` has applied this frame, not its base arc slot — and tests that point against `rect.rect` padded outward by `exitHysteresisPadding` (24 canvas units). Only an exit landing outside that expanded rect actually clears hover; one still inside it is treated as noise from the layout's own motion and ignored. **Applies to any future case where hover, drag-over, or similar pointer-relative state drives element movement that can feed back into pointer-relative detection** — the general shape of the bug is authoritative-but-naive event handling (trust the raw enter/exit) combined with a system that moves elements in response to that same event, which is exactly a feedback loop; the fix is always to make the *exit* condition read the element's current geometry with a hysteresis margin, not to try to prevent the element from moving.
31. **`OpponentHandPanel`/`opponentHandDisplay` is genuinely dual-purpose, not just "the opponent's hand" — its visibility must be gated by a runtime predicate, never a static "this is the opponent panel" flag.** Found scoping the opponent-hand-face-down work (Next Steps 19): the same `HandDisplay` instance and the same `List<CardInstance>` (`playerTwoHand.Hand`) serve two different intents depending on `manualControlMode` — the AI's genuinely-hidden hand (mode off) versus a fully human-playable hand when Craig manually drives Player Two by dragging from it (mode on, `CardDragResolver.CanPlayerTwoDrag` already gates the drag on the same flag). Concealing this panel unconditionally would have silently broken manual-control testing of Player Two, a real and already-relied-on capability (see the drag-and-drop playtest history). **Fix**: `HandDisplay.RenderHand`'s new `faceDown` parameter is a `Func<bool>` wired at the call site as `() => !manualControlMode`, evaluated fresh on every render rather than baked into which panel is being drawn — mirroring `CanPlayerTwoDrag`'s own `isManualControlMode()` check so the two stay consistent with each other. **Accepted, deliberately not fixed**: toggling `manualControlMode` in the Inspector doesn't itself trigger a re-render (`EffectTester` has no `Update()` polling it, matching `BoardDisplay`'s pre-existing `showAttackEligibility: ... && manualControlMode` having the identical lag) — the hand's face state only updates on the next natural `RefreshHandDisplay()` call (a card played, a turn ending, mulligan confirm), which is an acceptable one-refresh delay for a debug affordance. **Applies to any future feature that treats `OpponentHandPanel`/`opponentBoardPanel`/`opponentFaceView` as "belonging to the AI"** — check whether `manualControlMode` can put a human in control of what that view represents before gating anything on panel identity alone.

- ✅ **RESOLVED AT THE ROOT (this session)** — `CardData` reference identity. Two "copies" of a card were always the same `ScriptableObject` asset reference (`EffectTester.BuildDeck` adds it `copiesPerCard` times), which kept producing scoped bugs anywhere code keyed off `CardData` identity to distinguish them; `Hand.Contains`/`Remove` were blind to it, relying on the caller passing a list with correct multiplicity rather than on `CardData` itself being distinguishable. **Three occurrences of this bug class before this fix, each patched with a scoped workaround (track by something actually distinct per copy, not by `CardData`), never the root cause**: session 31's spell-targeting pending-selection state, fixed by tracking hand-index instead of `CardData` (old Constraint 17, since removed with the click flow it served); and the `MulliganController` selection bug — a `HashSet<CardData>` couldn't represent "both copies of a duplicate selected," so selecting the second copy silently toggled the shared entry back off and the card never entered the mulligan set at all — fixed at the time by switching to `HashSet<CardView>` (tracking the actually-distinct per-slot instance).

  **The root fix: `CardInstance` (new, `Scripts/Cards/CardInstance.cs`)** — a plain C# wrapper (`public CardData Data`, set via constructor) with no `Equals`/`GetHashCode` override, so two instances wrapping the same duplicate `CardData` are guaranteed distinct under default reference equality. `PlayerHand.Hand`/`.Deck` are now `List<CardInstance>`; the wrap happens exactly once, at the boundary — `PlayerHand`'s constructor and `AddCardToHand(CardData)` are the only places a raw `CardData` becomes a `CardInstance` (each entry of `BuildDeck`'s repeated-reference deck list gets its own instance there). Every downstream consumer (`HandDisplay`, `CardView`, `CardDragResolver`, `MulliganController`, `AIController`) now reads/writes `CardInstance` and accesses card data through `.Data`. `EffectTester` needed **zero changes** — `cardPool`/`coinCard`/`BuildDeck` all stay `CardData`, since the wrap boundary is entirely inside `PlayerHand`'s public API.

  **Chosen over two alternatives, deliberately**: (1) index-based tracking — rejected because it's the exact mechanism the old Constraint 17 workaround already used and had removed; indices shift under `Remove`/`Shuffle`/refresh, so every consumer would need to reason about *when* its index is still valid, which had already proven fragile once. (2) Cloning the `CardData` `ScriptableObject` per copy (`Instantiate(cardData)`) — rejected because it turns static, shared, authored card-definition assets into throwaway Unity `Object`s needing explicit `Destroy` lifecycle management, and fights the precedent `Minion` already established: wrapping shared card stats in a plain class rather than cloning the asset. `CardInstance` just extends that same pattern to hand/deck cards.

  **The `MulliganController` `HashSet<CardView>` workaround is removed as part of this fix** — `mulliganSelections` is `HashSet<CardInstance>` directly, and `CardView.SetCardForMulligan`'s toggle callback now passes the `CardInstance` itself instead of `this`. Once `CardInstance` gave duplicate cards real identity, the `CardView`-as-identity-proxy indirection had no remaining purpose — consistent with "one identity mechanism, not two competing ones," rather than leaving a second, now-redundant pattern for the same problem sitting alongside the new one.

  **This is a genuine architecture fix, not a fourth scoped workaround**: unlike the prior two fixes (hand-index tracking, then `CardView`-instance tracking), which each patched the *symptom* at the one call site that broke, `CardInstance` gives `CardData`-in-a-collection real identity everywhere at once — every `Hand`/`Deck` consumer now operates on that identity directly rather than tracking some other proxy to work around `CardData` not having one.
