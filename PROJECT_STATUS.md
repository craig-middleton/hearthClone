## Project Goal
Hearthstone-style card game in Unity, single-player vs AI, C# with data-driven cards/effects (ScriptableObjects). Ubuntu, Unity + VS Code, Git/GitHub with LFS for art/audio. Repo: `github.com/craig-middleton/hearthClone`.

**Unity 6.5 (60000.5.2f1).** TextMeshPro for all UI text, never legacy `UnityEngine.UI.Text`.

## Architecture
- Folders under `Assets/_Project/`: Scripts, ScriptableObjects, Prefabs, Art, Scenes. Cards are data-driven — they reference reusable `CardEffect` assets.
- **Assembly Definitions** enforce one-way flow: `Core` (no deps) ← `Effects` (Core) ← `Cards` (Core, Effects) ← `AI` (Core, Cards, Effects) ← `UI` (Core, Cards, Effects, **AI**, TMP). `Effects` must NOT reference `Cards`; `UI` references `AI` because `EffectTester` constructs `AIController`.
- **Keep `Core` generic and unaware of `CardData`.** AI-ness isn't a flag on `Player`.

### Design principles in force
Named only; reasoning and worked examples in HISTORY under Lessons Learned.
- **Rules live at the chokepoint** · **a rule is only centralised if its *inputs* are too** (`TryAttack` derives the defender rather than accepting it) · **guard *before* you instantiate** · **hiding something from the view doesn't remove it from state** · **reference identity: `Minion` is safe, `CardData` is not** · **"two of something" is a second *instance***, not code juggling two lists.

1. **`Board.GetTauntMinions(Player)` MUST NEVER RETURN NULL.** `Combat.TryAttack` calls `.Count` on it directly, so a null-returning guard here reintroduces an NRE there. `List.FindAll` already returns an empty list — the correct "no Taunts" answer.
2. **`Board.GetTauntMinions` has two call sites**: `Combat.TryAttack` (the rule) and `AIController` (its targeting heuristic). The *rule* lives in one place, the *lookup* in two — **changing it means checking both.**
3. **`Board.GetOwnerOf(Minion)` returns null** when the minion is on neither board. Callers must handle null.
4. **`Combat.TryAttack` guard order**: null attacker/target → null board → malformed `Target` → derive defender → attacker `IsDead` → target minion `IsDead` → defender null → own-side → Taunt → `CanAttack`. Taunt sits *above* `CanAttack` for message precedence; dead-attacker above both, since `CanAttack` includes `!IsDead` and would otherwise blame "summoning sickness" for a corpse.
5. **Accepted gap in `Combat.TryAttack`**: an attacker on neither board passes the own-side check (`GetOwnerOf(attacker)` is null, `defender` isn't). `attacker.IsDead` covers the realistic case; the rest needs a caller fabricating an off-board `Minion`. Deliberately unguarded.
6. **`EffectTester.AfterGameAction()` order**: `RemoveDeadMinions()` → drop a dead `selectedAttacker` → `RefreshAll()` → `CheckWinCondition()`. The drop must stay *before* the refresh. Called by *every* state-changing path.
7. **`EffectTester.ResolveAttack` clears `selectedAttacker` only on success** — a rejected attack deliberately keeps the selection for retargeting.
8. **`HandDisplay.RenderHand` and `BoardDisplay.RenderBoard` are structurally identical by design** — same guards in the same order. 12. **Older `CardData` assets physically omit later-added fields.**
    - **State**: `hasTaunt` is absent from **14 of the 16** assets (present only on `TestCard_Shieldbearer` as `1` and `TestCard_Goblin` as `0`). `artwork` and `description` are present on all 16. Git shows it cleanly: `targetsSelf` landed in `48e9d98`, and the ten-card batch created two commits later (`8963670`) has it; `hasTaunt` landed in `b2c217f`, five commits *after* that batch, so every asset lacks it except the two re-saved since.     - ✅ **New assets are fine.** A card asset created *after* a field exists gets that field written at creation — which is exactly why the ten-card batch has `targetsSelf`. The hazard is confined to assets that already exist when the field is added.

14. **A child positioned with point anchors (`AnchorMin == AnchorMax`) and a fixed `SizeDelta` does NOT track its parent's actual resolved size** — its size is absolute, set once, independent of whatever `HorizontalLayoutGroup`/`VerticalLayoutGroup` later assigns the parent. `MinionView`'s `ArtworkImage` was point-anchored with `SizeDelta` hand-matched to the *design* size (160x220); under `BoardPanel`'s `HorizontalLayoutGroup` (`Control Child Size` on, no min width set on the `LayoutElement`), a board with enough minions to exceed the panel's width shrinks every `MinionView` root below 160x220 — but `ArtworkImage`, unaffected by the layout group (it's a grandchild, not a direct child), stayed at the fixed 160x220 and overflowed past the shrunk card. Invisible on minions with no artwork (`Image.enabled = false`), so only artwork-bearing minions (Goblin) appeared to render "bigger" than their neighbours, though the root `RectTransform` sizes were identical the whole time. **Fix**: `ArtworkImage` now uses stretch anchors (`AnchorMin {0,0}` / `AnchorMax {1,1}`, `SizeDelta {0,0}`) so it always exactly fills whatever size the root actually resolves to. **Any child meant to fill `MinionView` or `CardView`'s root must use stretch anchors, not point anchors with a size that merely matches today's design dimensions** — the design dimensions and the runtime-resolved size are only the same number by coincidence, not by construction.

16. **A lethal spell hit on a minion can destroy the target's `Transform` mid-animation — `SpellAnimationSequencer` must tolerate that, not assume the target survives.** Originally found via `EffectTester.ResolveSpell` (session 31, since removed — see Constraint 17); the same fix and same risk apply unchanged through `ResolveCardDrag` (session 32), which starts the travel coroutine (holding a live target `Transform`) *before* `AfterGameAction()` runs, identically; `AfterGameAction` calls `RemoveDeadMinions()` then `RefreshAll()` synchronously in the same frame, which destroys the dead minion's `MinionView` before the coroutine's next `yield` resumes — an exactly-lethal hit throws `MissingReferenceException` on the following frame's `targetView.position` read. **Fix**: `TravelAndReactRoutine` re-checks `targetView != null` every frame (Unity's overloaded operator correctly flags a destroyed-but-not-nulled `Object`) and falls back to the last position sampled before it died; the end-of-travel reaction call is skipped the same way if the target is gone. **Chosen over unconditionally snapshotting the target's position at cast time** (the same treatment already given the source side) because the target survives intact in the overwhelming majority of casts — only a lethal kill destroys it — and is deliberately tracked live so `FaceView`'s idle sway shows through during travel; an unconditional snapshot would silently kill that sway for every cast, not just lethal ones, to guard a one-frame-rare edge case. **Confirmed minion-only**: `FaceView` is never destroyed by a refresh (`RefreshFaceDisplay` only calls `SetPlayer()` on the existing instance), so a lethal face hit cannot hit this bug — playtest-confirmed, not assumed. **Superseded in part (this session) — see Constraint 22**: this constraint's `targetView != null` fallback machinery is still exactly correct and still runs unchanged, but its *consequence* changed. `MinionView`'s hold mechanism now keeps a lethally-hit minion's view alive (undestroyed) through the end of its spell-cast animation, so `targetView != null` at the impact check now reads **true** for a lethal hit too — meaning `PlayDamageReaction()` (the flash) **now fires on a killing blow**, where it was previously silently skipped by this exact null-check. That was never a documented *intended* behavior, just the accepted side effect of a fix that only guaranteed no-crash, not correct timing — the flash-on-lethal is a deliberate, confirmed improvement, not a regression of this constraint's fix. This constraint's core lesson (never assume a minion target survives to the end of travel) still stands as the reason the hold exists in the first place.

20. **Hand-editing Unity-generated `ProjectSettings/*.asset` YAML (e.g. `TagManager.asset`) is stricter and less forgiving than editing scene/prefab YAML, and fails silently.** Found adding the `UIParticles` layer for the spell-VFX plan's isolated `ParticleSystem` render test (Next Steps, spell VFX). Unity's asset parser is not a general-spec YAML parser — it expects the exact formatting it itself emits. Writing an empty layer slot as a bare `-` instead of Unity's own `- ` (dash **+ trailing space**) broke the parser's list-tracking state and cascaded into a full-file parse failure (`Parser Failure at line N: Expect ':' between key and value within mapping`, reported against an unrelated, untouched line further down the file — here, the `m_SortingLayers` block). The practical effect is much worse than a bad scene/prefab edit: **the entire settings file silently reverts to defaults** — no custom layers, tags, etc. — rather than failing to load just the one malformed object. **Exact failure signature, so this is recognized immediately next time instead of re-diagnosed from scratch:**
    - The edit "looks right" by inspection and even by `grep`/`cat` — the added value (e.g. the layer name) is genuinely present in the file.
    - The corresponding runtime lookup (`LayerMask.NameToLayer`, or the equivalent for whatever settings type) returns "not found" / default anyway.
    - **Restarting the Editor does NOT fix it** — ProjectSettings is only re-read on load, but the file itself is still malformed on disk, so every reload re-fails the same way.
    - **The Console shows no error.** The only place this surfaces is `Logs/Editor.log`, as a `Parser Failure` line — check that file, not the Console, not just the relevant Project Settings window (which only shows *fewer entries than expected*, with no error of its own, since it's reading whatever the parser fell back to).
    - **Remedy**: match Unity's own emitted formatting exactly, byte-for-byte, for the file type being touched — for `TagManager.asset` specifically, every empty layer slot is `- ` (dash, space, nothing else), never a bare `-`. When in doubt, diff a known-good copy of the same asset type rather than hand-formatting from memory.

22. **`MinionView`'s hold mechanism (`BeginHold`/`EndHold`/`IsHeld`) is the resolution of Constraint 15 — DONE, playtest-confirmed (this session) across lethal, non-lethal, and the combat-kill regression.** A counter-based (not bool, so overlapping holds can't clear each other early), TTL-bounded (`holdExpiresAt`, logged if a hold is ever swept by TTL instead of an explicit `EndHold()`) hold that `BoardDisplay.RenderBoard`'s destroy loop respects — a held child is skipped instead of destroyed. **Playtest checklist, all confirmed**: (1) combat kill — a minion killed in combat (never acquires a hold) still disappears exactly as instantly as before this session, zero regression from the unused-but-present machinery; (2) exactly-lethal spell hit — minion stays visible through the full travel + flash reaction + spell burst, *then* disappears, matching the fix's intent exactly; (3) non-lethal spell hit — unaffected, behaves as before. **Who may call `BeginHold`, and when it's safe**: only when the `Minion` a view represents has already been removed from the model (`Minion.IsDead` true, checked synchronously before any `yield`) — holding a still-*present* minion's view would make `RenderBoard`'s rebuild loop spawn a second, fresh view for the same still-modeled `Minion` while the held one lingers too, a visible on-screen duplicate. `SpellAnimationSequencer` is the first caller (Next Steps 18, step 2); `CardView`/`HandDisplay` are the intended next callers for lift/zoom and discard-off (Next Steps 17) — same mechanism, same rule about only holding what's actually gone from the model. **Whoever calls `BeginHold` owns calling `EndHold()` and explicitly `Destroy()`-ing the GameObject when done** — a held view is skipped on every future refresh until released, so nothing else will ever clean it up; the TTL is a safety net for a caller bug, not a substitute for this. See Constraint 16 for the resulting behavior change (flash-on-lethal now fires).
23. **A held view (Constraint 22) and a `HorizontalLayoutGroup`-controlled panel don't compose safely by default — the hold alone only stops the view being destroyed, it does nothing to stop it being repositioned.** Found via the Arcane-lethal spell-burst playtest (Next Steps 18, step 3): a burst rendered far to the left of its target minion's actual on-screen position, traced to `BoardDisplay.RenderBoard` — its destroy loop skips a held child (so it keeps its *old* sibling index) but the rebuild loop `Instantiate`s fresh views for every surviving minion as *new* children appended after it, so a minion that died mid-row ends up at sibling index 0 once its still-held view is the only survivor of the old set. `BoardPanel`/`OpponentBoardPanel` both carry a `HorizontalLayoutGroup` (and `MinionView`'s prefab a `LayoutElement`), so sibling index drives horizontal position directly — the layout group snaps the held view to the leftmost slot regardless of where it actually died. `SpellAnimationSequencer`'s position tracking (`lastKnownTargetPosition`, Constraint 16) was never the bug — it re-samples `targetView.position` live and faithfully reports wherever the view *actually* is; the view itself was silently misplaced upstream. **Not Arcane-specific** — same shared `BoardDisplay`/`MinionView` code path Fire's lethal case also goes through. Re-verified specifically for this fix (see Verification Status): Fire's lethal case against a non-leftmost minion showed the identical leftward-snap bug, confirming it went unnoticed in the original Fire playtest (Next Steps 18 step 2) only because that test's target happened to already be in the leftmost slot (sibling index 0 is a no-op for this bug) and/or because Fire's large, chaotic burst visually masked a modest offset that Arcane's tight, deliberate swirl made obvious. **Fix**: `MinionView.BeginHold`/`EndHold` now toggle `LayoutElement.ignoreLayout` (`true` on the first hold, `false` back once the hold count returns to zero, including via the TTL-expiry path) — pulling the held view out of the `HorizontalLayoutGroup`'s control entirely, freezing it exactly where it visually sits at the moment it's held, fully decoupled from whatever reflow happens to its rebuilt siblings. **Rejected alternative**: restoring the held view's original sibling index (`SetSiblingIndex`) instead. Doesn't hold up — a `HorizontalLayoutGroup` recalculates *every* child's position on any change to the group's children, not just the moved one, so the held view's pixel position still isn't guaranteed stable if the surviving siblings' count/spacing changes elsewhere in the row during the hold window; layout exclusion is also the semantically correct behavior regardless — a dying minion should die where it stood, not snap to a recalculated layout slot mid-animation. **Applies wherever else the hold mechanism reaches a layout-group-controlled panel**: `CardView`/`HandDisplay` are the next intended callers of the identical `BeginHold`/`EndHold` pattern (Constraint 15, Next Steps 17, for lift/zoom and discard-off) — confirmed (this session, `TestScene.unity`) that `HandPanel`/`OpponentHandPanel` **both also carry a `HorizontalLayoutGroup`**, so this is not a hypothetical for future work: `CardView`'s hold, when it's built, needs the identical `LayoutElement.ignoreLayout` exclusion from day one, not discovered again the hard way. **Second finding, same session, after the `ignoreLayout` fix landed**: position was then confirmed correct (Fire and Arcane both re-tested against a mid-row minion), but the held view started rendering *behind* its surviving siblings instead of in front of/alongside them. Root cause: `ignoreLayout` only excludes the held view from the `HorizontalLayoutGroup`'s **position** math — it does nothing to sibling index, and sibling index is what independently controls **draw order** in this project's setup (`MinionView`'s prefab carries no `Canvas`/`overrideSorting` of its own, so it draws purely by sibling position within `GameCanvas`, a single `Screen Space - Overlay` canvas). `RenderBoard`'s destroy loop leaves the held view at its *old, low* sibling index (skipped, not re-added), while the rebuild loop's `Instantiate`d survivors all land at *new, higher* indices (`Instantiate` appends as last child) — so the held view silently draws underneath them. **Fix**: `RenderBoard` now collects held children during the destroy pass and calls `SetAsLastSibling()` on each *after* the rebuild loop finishes, every call — not just once at `BeginHold` — since the rebuild loop re-appends survivors with fresh sibling indices on every refresh a hold spans, so a one-time reorder wouldn't survive the next refresh. Position (`ignoreLayout`) and draw order (`SetAsLastSibling`) are independent fixes for independent mechanisms that happen to share the same root symptom (a stale sibling index) — fixing one does not fix the other, and both were needed. **Same implication for the future `CardView`/`HandDisplay` hold**: if `CardView`'s prefab also has no per-instance `Canvas` override, `HandDisplay.RenderHand` will need the identical `SetAsLastSibling()` treatment alongside its `ignoreLayout` exclusion, not just the position fix alone.

**Both the position fix (`ignoreLayout`) and the draw-order fix (`SetAsLastSibling`) were playtest-confirmed correct in isolation** — re-tested against a mid-row exactly-lethal hit for both Fire and Arcane: burst rendered at the correct position, and rendered on top of the surviving siblings, not behind them. But combining them exposed a third bug (below), and the eventual fix **replaced both mechanisms above** rather than keeping them — recorded here as the final, correct state.

**RESOLVED — layout-reflow regression on surviving minions, third and final bug in this chain.** `ignoreLayout = true` removed the held view from the `HorizontalLayoutGroup`'s participant count entirely, not just from having its own position overridden — so with one fewer child counted, the *surviving* minions visibly reflowed/shifted into the space that would otherwise still include the held view's slot, instead of staying put during the held sequence. Investigation showed this wasn't fixable by adjusting `ignoreLayout` further — the group had to keep counting the held view for the survivors' positions to stay put at all. But that created a conflict with the standing draw-order fix: `SetAsLastSibling` and "stay a counted participant at the correct *relative* slot" both want to control the same single sibling-index value for two unrelated jobs (layout order vs. draw order), and only one can win it at a time. **Root cause, in hindsight, across all three bugs in this constraint**: sibling index was being used as the sole channel for two independent concerns (board position and render order) that only coincide by accident in a flat `HorizontalLayoutGroup` + single `Screen Space - Overlay` canvas setup — every fix attempt that left this shared-channel assumption in place just moved the collision to a different symptom.

**Final fix — two independent channels, one per concern:**
- **Position**: `MinionView.BeginHold`/`EndHold` no longer touch `LayoutElement.ignoreLayout` at all — the held view stays a normal, counted `HorizontalLayoutGroup` participant, same as any live minion. `BoardDisplay.RenderBoard` captures each held child's sibling index *before* its destroy/instantiate pass touches the hierarchy, then — after instantiating fresh survivor views (which `Instantiate` always appends as new last children) — rebuilds the full sibling order as a merge: survivors that belonged before the held view's pinned index keep their relative order first, the held view is reinserted at exactly that pinned index, then the remaining survivors follow. This works because `MinionView`'s `LayoutElement` already carries a fixed, content-independent `PreferredWidth`/`PreferredHeight` (160×220) rather than deriving size from live text/artwork, and `BoardPanel`/`OpponentBoardPanel`'s `HorizontalLayoutGroup` has `ChildForceExpand` off with `ChildControlWidth/Height` on — so with a stable participant count, stable per-child size, and the held view restored to its original relative position, the row's total preferred width and every slot's computed position are byte-identical to the pre-death arrangement; survivors don't move at all.
- **Draw order**: sibling index no longer has any draw-order responsibility. `MinionView` now lazily adds (or reuses) a `Canvas` component on itself and toggles `overrideSorting`/`sortingOrder` in `BeginHold`/`EndHold` (mirroring the existing lazy-`GetComponent` pattern the `LayoutElement` reference used to follow) — this renders the held view on top of its siblings via Unity's canvas-sorting system, completely independent of where it sits in the sibling list. `RenderBoard` no longer calls `SetAsLastSibling()` anywhere.

**Playtest-confirmed** (this session): 3-minion board, exactly-lethal spell on the middle minion — both survivors' `RectTransform.anchoredPosition` logged identical across every `RenderBoard` call spanning the hold (temporary debug logging, since removed), held minion stayed frozen in its correct middle slot, burst rendered on top, then it disappeared cleanly with no post-death reflow glitch. **Applies to the future `CardView`/`HandDisplay` hold** (Constraint 15, Next Steps 17): `HandPanel`/`OpponentHandPanel` also carry a `HorizontalLayoutGroup`, so that implementation should use this same two-channel pattern (counted participant + pinned sibling index for position, a local `overrideSorting` `Canvas` for draw order) from the start, not `ignoreLayout`/`SetAsLastSibling`.

**Next Steps 18 step 3 (Arcane) is now fully complete** — position, draw order, and layout stability are all playtest-confirmed with no open caveats.

## Known Issues — real, not fixed
- ✅ **RESOLVED (this session, Next Steps 6) — Mulligan could hand back the card you just returned.** The old per-card `MulliganCard()` did remove → add-to-deck → shuffle → draw *per card*, so a card mulliganed early in a multi-card mulligan could be shuffled back in before later draws in the same batch. Replaced with `PlayerHand.MulliganCards(List<CardData>)`: removes **all** selected cards from `Hand` first, draws that many replacements from the deck as it stood (excluding every set-aside card), and only *then* adds the set-aside cards back to `Deck` and shuffles once — matching real Hearthstone's batching. `MulliganController.OnConfirmMulliganClicked` and `AIController.PerformMulligan` both updated to collect their full selection and call `MulliganCards` once instead of looping. **Approved deliberate behaviour change**: because set-aside cards are no longer temporarily re-added to the deck before each draw, mulliganing more cards than remain in the deck can trigger fatigue where the old code wouldn't (only reachable with a near-empty deck, not a realistic 30-card game start) — this is correct "draw before shuffle-back" behaviour, not a regression.
